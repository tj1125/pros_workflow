\begin{abstract}

本論文旨在設計與實作一套以視覺語言模型（Vision-Language Model, VLM）與代理人架構（Agent Architecture）為核心之居家服務機器人系統，能將使用者以自然語言表達之高階語意請求（High-Level Semantic Request），透過代理人工作流程自動轉換為機器人可執行之低階控制指令（Low-Level Control）。本論文以居家環境為主要部署情境，期望使家中各類使用者（包含老人、行動不便者等）能以直覺且自然的語言方式，委派機器人協助完成日常生活中的各類服務任務，無需具備任何技術背景。為了印證系統的功能，論文使用數位孿生（Digital Twin）技術進行上述工作的模擬，包含環境建模與任務驗證。

此外，在居家場景中，環境資訊具有高度私密性，使用者之語音、影像與室內狀態等資料若上傳至雲端伺服器，將引發顯著的隱私疑慮。有鑑於此，本系統全面採用可於本地端運行之開源視覺語言模型，確保所有感知、推論與決策過程均在使用者家中的運算裝置上完成，資料不經由外部網路傳送，從根本上保障居家隱私安全。此設計亦使系統在無穩定網路連線的居家環境下仍能可靠運作。

在系統架構方面，我們整合 LangGraph 與 A2A（Agent-to-Agent）協議管理整體任務流程，將物體感知定位、場景理解、機器人導航與控制等功能拆分為可獨立呼叫之代理人模組。VLM 不直接輸出機器人之速度、關節角度或夾爪動作，而是根據當前任務狀態與觀察結果決定下一步應被觸發之機器代理人，再由 ROS2 控制節點發佈命令，該機器人可自主完成任務或是執行節點所接收之低階之命令。此架構使系統能根據環境變化持續調整行動策略，具備可追蹤、可重新估計與失敗回退能力，並允許後續在不重寫整體架構的前提下新增或替換功能模組，提升系統之可維護性與擴充彈性。

為驗證上述架構於居家環境中的實際可行性，本研究以「移動抓取」作為代表性示範任務，並整合 Unity 與 ROS2 建立室內數位孿生環境加以測試。示範情境設定為：目標物可以不在機器人初始視野範圍內，且任務執行過程中可能遭遇目標遮擋、導航失敗或觀察資訊不足等挑戰。系統透過環境相機預先估計目標物位置及尺寸，利用 GraspGen 產生無碰撞抓取姿態，並根據車載相機之即時觀察由 VLM 動態決策後續行動並自主完成，示範了從自然語言指令到實際抓取動作之完整閉環流程。實驗中亦觀察到，事先規劃適合之車體停靠點，使機器人抵達後能直接進入觀察與抓取流程，有效避免到達目標附近後仍需反覆調整底盤位置之問題，降低任務執行成本並提升整體流程之穩定性。

實驗結果顯示，在以 Unity 建立的居家數位孿生環境中，共 $200$ 次移動抓取消融實驗下，完整系統達到最高的成功率（$90\%$）；移除 VLM 觀察決策、候選 goal\_pose 排序，或物體 Size Dimension 估計後，成功率分別下降至 $78\%$、$44\%$ 與 $68\%$。這說明本研究的成效並非來自單一模組，而是由全域語意感知、多候選導航點排序與 VLM 閉環決策共同形成具失敗恢復能力的移動抓取流程，為居家服務機器人之落地部署與彈性擴充提供可行的系統設計參考。
\end{abstract}

\section{Introduction}

近年來，隨著大型語言模型（Large Language Model, LLM）與視覺語言模型（Vision-Language Model, VLM）的快速發展，機器人系統理解自然語言指令與視覺觀察的能力已有顯著提升，使居家服務機器人的實用化逐漸成為重要研究方向。相較於工廠或實驗室環境，居家場景具有物件種類多、擺放位置不固定、遮擋情況頻繁、使用者需求難以預先窮舉等特性。因此，理想的居家服務機器人不應只執行固定按鈕或預先寫死的腳本，而應能理解使用者以日常語言提出的需求，並自動將任務拆解成多個可執行步驟。

近期研究已開始探討如何將語言模型與機器人行為結合，例如利用語言模型進行高階行動選擇、將多模態感測資料整合至具身推理模型，或將視覺語言模型延伸至機器人動作生成。這些研究顯示，LLM/VLM 技術具備輔助機器人理解語意任務與規劃行動的潛力。然而，居家服務機器人要從自然語言指令真正執行任務，仍需同時處理物體定位、三維幾何、導航可行性、抓取姿態、安全檢查與失敗恢復。因此，如何將語意推理能力與可驗證的機器人控制流程結合，仍是居家服務機器人落地應用中的關鍵問題。

具體而言，從一句自然語言指令到實際機器人動作之間仍有多個未被直接指定的中間步驟。使用者可能只說「幫我拿桌上的杯子」，但機器人必須進一步判斷目標物是哪一個、物體是否在視野內、應導航到哪個位置觀察、手臂是否可達、抓取姿態是否會碰撞，以及失敗時應如何重新嘗試。這些問題同時涉及語意理解、三維幾何、路徑規劃、感測不確定性與低階控制，並非單一模型或單一控制節點即可完整處理。若直接要求 VLM 輸出速度、關節角度或夾爪控制等低階命令，則會面臨控制精度、安全性與物理可行性難以保證的問題；若只採用固定流程，則又難以應對遮擋、目標不在初始視野、導航失敗或抓取不可行等居家場景常見情況。

基於上述限制，本研究的動機是將傳統「單一機器人依固定流程完成任務」的設計，重新表述為「單一機器人由多個專責代理人共同協作完成任務」。在此觀點下，機器人仍是執行服務的實體，但其能力被拆解為多個功能明確的 agents，例如物體定位與Size Dimension 估計 agent、導航 agent、抓取姿態生成 agent、車體靠近與手臂控制 agent 等。VLM 不直接控制馬達或關節，而是根據目前任務狀態、觀察結果與歷史紀錄，選擇下一個應被觸發的 agent；需要精確幾何、安全檢查與硬體控制的部分，則交由專門模組處理。此設計使語言模型能發揮語意理解與流程決策能力，同時避免讓其直接承擔連續控制與物理可行性判斷。

本論文提出一套以 VLM 與代理人架構為核心之居家服務機器人系統，將高階語意理解與低階機器人控制明確解耦。在任務協調層面，本研究使用 LangGraph 維護長任務狀態，使系統能記錄目前目標、導航結果、車載觀察、抓取結果與失敗原因，並在觀察不足或執行失敗時回到合適節點重新估計或切換策略。對於 GraspGen、SAM （Segment Anything Model）與Size Dimension 估計等需要較高算力的推論服務，則透過 A2A（Agent-to-Agent）協議以獨立代理人方式整合，使不同功能模組能獨立部署、呼叫與替換。此外，居家環境中的影像、語音與室內狀態具有高度私密性，因此本研究將 VLM 決策與主要任務流程設計為可於本地端或受控環境中執行，以降低對外部雲端服務的依賴。

為具體說明此架構的運作方式，本研究以移動抓取任務作為代表性情境。系統首先透過環境相機取得目標物的全域位置與尺寸資訊，並據此規劃適合觀察與抓取的車體停靠點，使機器人能直接導航至合適位置，避免抵達後反覆調整底盤。當機器人抵達目標附近後，系統進一步啟用車載第一人稱相機進行近距離觀察，由 VLM 判斷當前視角是否足以進入抓取流程，或是否需要切換至其他停靠位置以取得更完整的場景資訊。在抓取流程中，系統結合 GraspGen 候選抓取姿態與 PyBullet 可達性及碰撞檢查，以降低執行時發生碰撞或不可達的風險。機器人控制層基於 ROS2（Robot Operating System 2）實現，並整合 Unity 數位孿生環境進行系統驗證。未來工作將進一步擴充更多居家任務設定，並將此代理人式流程推進至實體環境驗證。

\section{Related Works}

\subsection{Robots for Home Service}

\subsubsection{VLMs for Task Understanding}

近年來，大型語言模型（Large Language Model, LLM）與 VLM 逐漸被應用於機器人任務理解與高階決策中。對於實體機器人而言，使用者的自然語言指令通常只描述任務目標，例如拿取、搬運或整理物件，而不會明確指定機器人應執行的技能序列、導航終點、手臂姿態或控制參數。因此，機器人系統需要將高階語意請求轉換為可執行的行為流程，並在過程中考慮目前環境狀態與機器人自身能力。

SayCan 是將大型語言模型應用於機器人任務理解與技能選擇的代表性工作之一。該方法並不直接讓語言模型輸出低階控制命令，而是將語言模型對候選技能「是否符合任務語意」的評估，與機器人 value function 對該技能「是否能在目前狀態成功執行」的評估結合，使系統能選擇同時有用且可執行的下一個技能 \cite{ahn2022saycan}. 這種設計突顯了 LLM 在機器人系統中的適當角色：模型可協助判斷任務意圖與高階行為順序，但實際執行仍需由預先定義的技能、控制器或規劃模組負責。

此後，LLM-based robot planning 的研究逐漸從單次技能選擇延伸到較長時序的任務規劃與執行監控。BrainBody-LLM 將機器人任務分為 high-level planning 與 low-level control，並利用模擬器或控制器回傳的錯誤作為 closed-loop state feedback，使系統能在計畫無法執行時進行修正 \cite{bhat2024brainbody}. 此類方法指出，語言模型生成的計畫若缺乏執行回饋，可能會在實際環境中因物體位置、可達性、動作限制或控制失敗而無法完成。因此，任務理解不應只停留在語意層面，也必須與環境狀態和執行結果形成閉環。

針對服務型機器人，LLM-based Robot Task Planning with Exceptional Handling 進一步探討語言模型在一般服務機器人任務中的例外處理問題。該研究透過 constrained prompt 與 exceptional handling module，限制 LLM 產生符合目前環境與可接受動作集合的 action sequence，並降低模型 hallucination 對任務執行造成的影響 \cite{wang2024exception}. 這說明在實體機器人應用中，LLM/VLM 的輸出需要受到任務狀態、可執行動作集合與錯誤恢復機制的約束，而不能僅依賴模型本身的自由生成能力。

除了線性任務計畫，也有研究將 LLM 與結構化任務表示結合。LLM-as-BT-Planner 使用 LLM 生成 Behavior Tree，以支援 robotic assembly task planning and execution \cite{ao2024btplanner}. Behavior Tree 具有模組化、條件分支、狀態檢查與失敗恢復等特性，因此適合描述需要反覆觀察、判斷與執行的機器人任務。相較於單純文字形式的 action list，結構化 workflow 更有助於將模型推理結果銜接到實際機器人系統。

在多代理人機器人任務方面，MALMM 提出 multi-agent large language model framework，將 high-level planning、low-level control code generation 與 transition management 分配給不同 agents，並透過環境觀察進行 adaptive re-planning \cite{singh2024malmm}. 這類方法反映出近期 robotic AI agent 的一個重要趨勢：複雜機器人任務往往不適合由單一模型一次完成，而需要透過多個具不同職責的模組或代理人協同完成任務理解、規劃、執行與修正。

\subsubsection{Home Service Robots and Mobile Manipulation}

在居家服務機器人方面，系統需要將使用者的自然語言需求，轉換成實際環境中的目標搜尋、物件辨識、移動導航與抓取操作。由於居家場景通常包含多房間、多物件、遮擋與未知物件類別，機器人不僅需要理解任務語意，也需要根據目前環境狀態決定如何移動、從哪個角度觀察目標，以及是否具備可執行的操作條件。因此，如何讓機器人在未知居家場景中理解自然語言指令並正確執行任務，成為居家服務機器人研究中的重要課題。

HomeRobot 提出 Open-Vocabulary Mobile Manipulation（OVMM）問題，將其定義為機器人在未知環境中抓取任意物件，並將其放置到指定位置的任務 \cite{yenamandra2023homerobot}. 該研究指出，OVMM 同時涉及感知、語言理解、導航與操作，而這些子系統的整合本身即是一項重要挑戰。此問題定義與本研究的任務脈絡相近：使用者以自然語言指定目標物，系統需要在環境中確認實際目標，估計其空間位置，移動至適合觀察與操作的位置，並進一步完成抓取。不同的是，HomeRobot 的標準任務包含完整的抓取與放置；本研究則聚焦於 OVMM 脈絡下的自然語言驅動移動抓取流程，亦即將開放詞彙目標理解、移動導航與抓取執行整合為可追蹤的閉環任務。

在 open-vocabulary mobile manipulation 中，語意理解與空間定位需要被共同處理。LOVMM 提出 Language-conditioned Open-Vocabulary Mobile Manipulation 架構，將 LLM 與 VLM 納入家庭環境中的移動操作任務，用以處理自然語言指令與未知物件操作 \cite{tan2025lovmm}. 此類方法顯示，居家移動操作不應只依賴固定類別偵測，而需要讓自然語言描述、視覺觀察與任務流程相互銜接。本研究採取相似的問題設定，但系統並不訓練新的操作策略，而是將 VLM 限制為高階流程判斷模組。使用者輸入經任務分類與目標候選確認後，VLM 僅在預先定義的代理人模組間進行選擇；實際的物件資訊估計、導航、抓取姿態生成與低階控制則由專門模組負責。

除了語意理解，OVMM 也需要維持可用的場景資訊。DynaMem 提出一種用於開放世界移動操作的動態三維語意記憶方法，讓機器人能以三維點雲形式記錄環境，並透過多模態語言模型或開放詞彙視覺特徵回答物件位置查詢 \cite{liu2024dynamem}. 該方向說明，居家移動操作不能只依賴單次物件偵測，因為物件可能移動、出現或消失，系統需要在任務過程中持續更新場景狀態。本研究雖未建立完整的長期語意記憶地圖，但在任務流程中使用房間相機、多視角世界座標與車載觀察來更新目標資訊；若目標位置變動超過設定門檻，系統會清除舊的物件資訊與導航狀態，重新估計目標位置與候選導航點。

另一些研究則從三維語意地圖與線上規劃角度處理 OVMM。Open-vocabulary Mobile Manipulation in Unseen Dynamic Environments with 3D Semantic Maps 結合 VLM 的開放詞彙偵測、三維物件重建、LLM 空間推理與線上規劃，使機器人能在未知且會變動的環境中，根據三維語意地圖執行任務 \cite{qiu2024ovmm3dsemantic}. 這類方法強調，語言與視覺理解需要被轉換為可供導航與操作使用的空間表示，才能支援目標搜尋、路徑規劃與操作位置判斷。本研究採取較工程化且可落地的做法：系統使用 Unity 的世界座標與多視角觀察估計目標位置，再將目標中心、地圖可通行性與抓取方向轉換為排序後的導航候選點，使機器人能優先移動至較適合觀察與抓取的位置。

\subsection{AI Agents and Workflows}

\subsubsection{LangChain and LangGraph}

LangChain 是一套用於建立 LLM 應用與代理人的開源框架，提供模型呼叫、prompt 管理、工具整合、資料檢索與 agent 等抽象介面，使開發者能快速串接不同模型、向量資料庫、API 與外部工具。對一般 LLM 應用而言，LangChain 的優點在於整合性高、工具生態完整，適合快速建立 retrieval-augmented generation、tool-using agent 與多模型串接應用。

在 LangChain 生態中，相關工具可依功能分為下列幾類。第一，LangChain library 主要提供模型、prompt、retriever、tool 與 agent 的基礎組件，用於建立一般 LLM 應用與工具呼叫流程。第二，LangSmith 偏向觀測、除錯與評估，可用於追蹤 LLM 應用的輸入輸出、工具呼叫、錯誤原因與執行紀錄。第三，LangGraph 則是同一生態中的代理人流程協調框架，主要用於建立長時間執行、具狀態且需要分支或循環的工作流程。

LangGraph 的核心概念是將任務表示為由節點與邊構成的狀態圖。每個節點對應一個明確的任務步驟或工具呼叫，邊則描述節點之間的轉移條件；共享狀態可在節點間傳遞與更新，使系統能記錄目前任務進度、觀察結果、模型決策與執行回饋。官方文件將 LangGraph 定位為用於建立長時間執行、具狀態 workflow 或 agent 的框架，並強調其支援 durable execution、streaming、human-in-the-loop 與 memory 等能力 \cite{langgraph_workflows}。相較於一般線性 chain，LangGraph 更適合描述具有分支、循環、重試與恢復機制的任務。

本研究選擇 LangGraph 作為任務流程管理工具，主要是因為機器人任務具有長時間執行、多階段狀態、外部感測回饋與錯誤恢復等特性，難以僅用一般線性 chain 或單次 agent loop 清楚描述。以移動抓取任務為例，系統可能因導航失敗、目標遮擋、觀察不足或抓取不可行，而需要切換候選路徑或返回前一階段重新判斷。LangGraph 的狀態圖設計能將不同任務階段表示為可追蹤的節點，並透過共享狀態保存觀察結果、模型決策、工具輸出與失敗原因，使後續節點能依目前狀態進行條件路由與重試。因此，LangGraph 較一般 LangChain chain 更符合本研究所需的長任務、閉環控制與失敗恢復需求。

\subsubsection{A2A}

A2A 是一種用於代理人之間通訊與協作的開放協定，目標是讓由不同框架、不同服務或不同環境建立的 AI 代理人，能以一致的方式交換訊息、委派任務並回傳結果 \cite{a2a_spec}。在 A2A 架構中，A2A Client 是發起請求的一方，負責向其他代理人送出任務請求；A2A Server，也可稱為 Remote Agent，則是提供 A2A endpoint 的一方，負責接收請求、執行任務並回傳結果。A2A Server 會透過 Agent Card 描述自身名稱、能力、服務端點與可提供的功能，使 Client 能知道該代理人適合處理哪些任務。除此之外，A2A 也定義 Message、Task 與 Artifact 等概念，用於表示代理人之間的訊息交換、任務狀態與任務產生的結果。

在安全性方面，A2A 提供的是代理人通訊與任務委派的標準格式，實際安全性仍取決於系統部署方式與存取控制設計。由於 Agent Card 可能包含服務端點、代理人能力與認證需求，若直接暴露在公開網路中，可能造成未授權呼叫或能力資訊外洩。因此，在實務部署上，A2A 服務應搭配身分驗證、權限控管、加密通訊、內網限制與日誌紀錄等機制。若部署於地端或受控網路環境，A2A 可讓不同推論代理人在本地網路中交換任務與結果，降低影像、場景資訊或模型輸出傳送至外部雲端服務的需求。

本研究並非將 A2A 作為整體系統的主要通訊架構，而是在 LangGraph workflow 的特定節點中使用 A2A 呼叫遠端 agent。當流程執行到需要外部推論能力的階段時，該節點會扮演 A2A Client，依任務需求向對應的 A2A Server 發送請求，並將遠端 agent 回傳的結果寫回 workflow state，供後續節點使用。透過這種方式，較高成本或較專門化的推論模組可以獨立部署為 Remote Agent，而主流程不需要直接綁定各模型或服務的內部實作。此設計使系統在維持 workflow 結構清楚的同時，也方便日後替換模型、調整推論服務或新增新的 agent 功能。

\subsubsection{Workflow Automation Tools}

除了前述用於代理人流程管理的 LangGraph，以及用於代理人之間通訊的 A2A 之外，工作流程自動化工具也常被用於串接不同應用與服務。這類工具通常以視覺化流程為核心，讓使用者透過觸發條件、節點與連線關係建立跨系統流程。常見工具包含 Zapier、Make 與 n8n：

\begin{itemize}
  \item Zapier：Zapier 的特色在於應用整合數量多，主要面向商務使用者與一般團隊。它支援大量雲端服務，讓使用者能將 Gmail、Slack、Google Sheets、Notion、CRM、表單工具與 AI 服務等應用串接成自動化流程。Zapier 的優勢是上手門檻低、既有應用支援完整，適合處理通知、表單回覆、資料同步、客戶關係管理與辦公室日常自動化。其近年的 AI workflows 與 AI agents 功能，也延續這個方向，讓 AI 能直接和既有雲端應用一起運作。
  \item Make：Make 的特色在於視覺化流程設計與資料流控制。相較於以「觸發條件加動作」為主的簡單自動化，Make 更強調在畫布上建立多步驟流程，使用者可以清楚看到每個模組之間的資料傳遞、條件分支、資料轉換與錯誤處理。因此，Make 較適合需要觀察流程結構、設計多分支路徑、處理多個服務之間資料轉換的自動化情境。它的優勢不是單純應用數量，而是讓流程邏輯與資料流向更容易被設計與檢查。
  \item n8n：n8n 的特色在於技術彈性與自架部署 \cite{n8n_nodes}。它同樣提供視覺化流程設計，但更強調自訂程式碼、API 呼叫、資料庫連接、AI 節點，以及與內部服務或私有資料庫的整合。相較於主要面向雲端服務串接的工具，n8n 更適合技術團隊建立可控程度較高的自動化流程，也適合部署在自己的伺服器上，與自架模型、內部 API 或本地資料服務整合。
\end{itemize}

本研究選擇 LangGraph 作為主要流程管理工具，而非 Zapier、Make 或 n8n 這類工作流程自動化工具，原因在於相較之下，LangGraph 可直接以程式碼定義節點邏輯、共享狀態、條件路由、循環與錯誤恢復，使系統能根據模型輸出、工具結果與失敗原因動態決定下一步，讓整體工作流程能更加彈性。

\subsection{ROS2-Unity Digital Twin Robot Platform}

\subsubsection{ROS2}

ROS2 是機器人系統中常用的通訊與軟體整合架構，其設計目標是將複雜的機器人系統拆分成多個可獨立執行的節點。每個節點負責特定功能，例如感測資料接收、導航、控制、影像處理或任務執行；節點之間則透過 ROS2 提供的通訊機制交換資料。這種模組化設計使不同功能可以分開開發、測試與替換，也使大型機器人系統能夠由多個獨立程式共同組成。

ROS2 的主要通訊方式包含 topic、service 與 action \cite{ros2_interfaces}。Topic 採用 publish/subscribe 模式，適合持續傳送資料，例如感測器資料、影像、位置資訊或控制指令。發布端只需將資料送到指定 topic，訂閱端即可接收對應訊息，因此 topic 適合用於高頻率或連續性的資料交換。Service 採用 request/response 模式，適合處理一次性的請求與回覆，例如查詢狀態、取得參數或執行短時間計算。Action 則適合用於較長時間的任務，例如導航到指定位置或執行一段動作；它除了能送出目標與取得最終結果，也能在執行過程中回傳進度，並支援取消任務。
ROS2 底層使用 DDS 作為通訊基礎，使節點能在同一台電腦、不同程序，甚至不同機器之間進行分散式通訊。DDS 也提供 QoS 設定，使開發者能依照資料特性調整可靠性、佇列深度、延遲與資料保存方式。對機器人系統而言，不同資料對通訊品質的需求並不相同：感測器資料通常重視即時性，控制命令可能更重視穩定傳遞，而任務狀態則需要能被後續節點正確取得。因此，ROS2 的 topic、service、action 與 QoS 設計，能讓不同類型的機器人資料採用合適的通訊方式。

\subsubsection{SLAM}

SLAM（Simultaneous Localization and Mapping）是移動機器人導航中的基礎技術，目標是在未知環境中同時估計機器人自身位置，並建立周圍環境的地圖。對室內移動機器人而言，常見做法是利用 LiDAR（Light Detection and Ranging）、depth camera、odometry 與 IMU（Inertial Measurement Unit）等感測資料，估計機器人的移動軌跡，並將牆面、障礙物與可通行區域建立成 occupancy grid map，供後續 localization、path planning 與 navigation 使用。在 ROS2 生態中，slam\_toolbox 是常見的 2D SLAM 工具，支援 mapping、localization、map saving 與 map reloading 等功能 \cite{slam_toolbox}。

\subsubsection{Nav2}

Nav2（Navigation2）是 ROS2 中常用的 mobile robot navigation framework，負責讓機器人根據目前 pose、目標 pose 與環境地圖，自動規劃並執行移動路徑 \cite{nav2_concepts}。Nav2 並不是單一演算法，而是由多個模組組成的 navigation stack，包含 planner、controller、costmap、behavior tree 與 recovery behavior 等元件。Planner 負責根據地圖產生從目前位置到目標位置的 path；controller 則根據機器人附近的環境資訊與運動限制，產生實際 velocity command，使機器人沿著 path 前進；costmap 則將障礙物、膨脹區域與可通行空間轉換成 navigation 可使用的空間表示。

Nav2 的另一個特色是使用 behavior tree 管理 navigation task。透過 behavior tree，導航流程可以被拆分成 path planning、path following、goal checking、failure detection 與 recovery behavior 等步驟。當導航過程中發生 path 不可行、障礙物阻擋或控制失敗時，系統可以重新規劃路徑、清除 costmap，或執行其他 recovery behavior。這使 Nav2 不只是輸出一條固定路徑，而是能在任務執行過程中根據狀態進行調整。

在 path generation 方面，Nav2 由 Planner Server 接收 navigation goal，並呼叫對應的 planner plugin 產生 path。既有系統使用 SmacPlanner2D 作為 global planner；SmacPlanner2D 屬於 Nav2 Smac Planner 系列，採用 A*-based path planning，可根據 costmap 與 navigation goal 產生可通行路徑。路徑產生後，Controller Server 會透過 FollowPath controller 執行 path following。既有系統中的 FollowPath 由 RotationShimController 與 DWBLocalPlanner 組成，其中 RotationShimController 用於在開始追蹤新路徑時修正機器人朝向，DWBLocalPlanner 則根據局部環境與候選速度產生可執行的 velocity command。透過 planner 與 controller 的分工，Nav2 能先產生全域移動路徑，再於執行過程中根據局部環境輸出實際控制命令。

\subsubsection{pros System}

pros System 是基於 ROS2-Unity 數位孿生平台中的底層控制系統，主要負責系統啟動、模組管理、車體導航控制與機械手臂操作 \cite{yushiang2025}。該系統建立在 ROS2 架構上，並將不同功能拆分為獨立套件，使 Unity 數位孿生環境能透過 ROS2 通訊機制接收控制訊號，並執行對應的車體與手臂動作。pros System 的主要組成如下：

\begin{itemize}
  \item pros\_app：負責系統啟動與模組管理。pros\_app 提供 Terminal UI 作為操作入口，並透過 Python script 顯示選單與接收使用者輸入。當使用者選擇特定功能後，pros\_app 會呼叫對應的 shell script，接著啟動 Docker Compose 建立執行環境，並透過 ROS launch files 啟動相關 ROS 節點。由於 ROS2 系統包含多個需要共同運作的節點，pros\_app 將啟動流程包裝成可操作的介面，使使用者能以一致方式啟動 SLAM、Camera、導航與控制等模組。
  \item pros\_car：負責機器人操作邏輯，內部可分為 Central Control、Car Control 與 Arm Control。Central Control 作為任務分配中心，負責協調車體與手臂任務，並將導航或夾取等執行時間較長的任務派送至對應控制模組。Car Control 負責車體導航與移動控制，Arm Control 負責機械手臂動作與夾取流程。此分層方式將任務協調、車體控制與手臂控制分開，使各模組的責任範圍更清楚，也降低控制流程之間的耦合。
  \item ROS2 控制方式：pros\_car 以 action server 管理 navigation 與 grasping 等執行時間較長的任務。Car Control 的 action server 接收 navigation goal 並負責任務執行狀態管理；Arm Control 的 action server 則負責 grasping 任務的執行流程。由於 action server 管理的是任務層級的 goal、feedback 與 result，實際車體與手臂的控制命令仍需在任務執行過程中發布至對應 topic。根據既有系統設計，車體控制命令發布至 \texttt{car\_C\_rear\_wheel} 與 \texttt{car\_C\_front\_wheel}，機械手臂控制命令則以 \texttt{JointTrajectoryPoint} 訊息發布至 \texttt{/robot\_arm}。換言之，action server 負責管理任務狀態，topic 則負責傳送實際控制命令。
  \item Follow path：在導航控制方面，pros\_car 使用 Nav2 產生的 path 進行車體控制。Car Control 會根據目前車體位置、navigation goal、Nav2 path 上的 local target point 與車體朝向計算 heading error。當車體尚未抵達 navigation goal 時，系統會沿 path 選取下一個 local target point，並比較車體目前朝向與該目標點方向的角度差。若 heading error 過大，車體會先旋轉修正方向；若 heading error 在可接受範圍內，車體則向前移動。當車體接近 navigation goal 後，系統會停止導航流程，並依後續任務狀態進入觀察、對準或操作階段。
\end{itemize}

\subsubsection{Unity-Based Digital Twin Environment}

Unity 是本研究用於建立居家機器人任務場景的模擬環境。本研究使用自建居家場景作為主要測試空間，並延續既有 ROS2-Unity 數位孿生平台的基本設定，使 Unity 場景中的機器人、相機、物件與環境資訊能與 ROS2 控制流程連接 \cite{yushiang2025}。Unity 端負責呈現居家場景、機器人模型、車載相機與環境相機，並提供任務執行所需的影像與感測器資訊。透過此可視化且可重複測試的居家場景，本研究能驗證自然語言任務理解、目標確認、候選導航點選擇、車載觀察與移動抓取流程。

\subsection{Visual Perception and 3D Scene Understanding}

\subsubsection{Camera Calibration}

在相機成像過程中，3D 空間中的點會經由相機模型投影到 2D 影像平面，因此若要由影像座標推回空間關係，必須先取得相機的內參與外參。內參用於描述相機本身的成像特性，包含焦距與主點位置；外參則描述相機座標系與外部座標系之間的相對姿態，通常以 rotation 與 translation 表示。除此之外，實際鏡頭也會產生徑向與切向畸變，使影像中的直線、邊界與投影位置產生偏移，因此需要透過 camera calibration 估計並修正這些參數。

OpenCV 的 camera calibration 流程通常使用 chessboard 作為 calibration pattern \cite{opencv_calib}。棋盤格角點具有規則且已知的幾何排列，可作為影像點與空間點之間的對應基準。校正時，系統會從多張不同角度與距離拍攝的 chessboard 影像中偵測角點，並將影像中的 2D corner points 對應到棋盤格上已知位置的 3D object points。接著，OpenCV 可透過這些對應關係估計 camera matrix、distortion coefficients、rotation vectors 與 translation vectors。

\subsubsection{YOLO}

YOLO（You Only Look Once）是一種常用於即時物件偵測的深度學習模型，其核心概念是將物件分類與位置回歸整合在單一次前向推論中完成，因此能在影像或影片中快速預測物件類別與 bounding box \cite{ultralytics_yolo}。相較於需要多階段候選區域生成的偵測方法，YOLO 系列模型以端到端方式直接輸出偵測結果，因此常被應用於需要即時反應的機器人視覺任務。

本研究使用 Ultralytics YOLO26 作為物件偵測模型，用於辨識 Unity 居家場景中的目標物。YOLO26 延續 YOLO 系列重視即時性的設計，並加入 end-to-end NMS-free inference，使模型能直接產生偵測結果，降低後處理流程對推論延遲的影響。此外，YOLO26 也針對 edge 與 low-power devices 進行最佳化，並透過改良的訓練策略提升小物件偵測能力。本研究以 YOLO26 pretrained model 作為微調的初始權重，並使用 Roboflow 平台建立與訓練自訂資料集。透過 Roboflow 進行影像標註、資料集管理與模型訓練後，得到能辨識本研究目標物的 YOLO26 偵測模型。模型輸出的類別與 bounding box 會作為後續目標確認、候選導航點選擇、車載觀察與移動抓取流程的視覺依據。

\subsubsection{SAM}

SAM（Segment Anything Model）是由 Meta AI 提出的影像分割基礎模型，目標是讓模型能根據不同形式的提示產生物件遮罩 \cite{sam}。相較於一般物件偵測模型主要輸出 bounding box，SAM 著重於產生像素層級的 segmentation mask，因此能更精確地描述物件輪廓。原始 SAM 可透過 point、box 或 mask prompt 對影像中的物件進行分割，並具備良好的 zero-shot segmentation 能力。後續的 SAM 2 將此能力延伸至 image 與 video segmentation，使模型能在影片中追蹤並分割目標物。SAM 3 則進一步支援以文字、影像範例與視覺提示進行 detection、segmentation 與 tracking；SAM 3D 則將 SAM 系列的概念延伸至 3D reconstruction 與 3D perception 任務。本研究使用 SAM 作為輔助視覺模組，用於取得目標物更精細的 segmentation mask，使系統在物件定位、目標確認與後續移動抓取流程中能取得比 bounding box 更完整的物件區域資訊。

\subsubsection{Object Localization}

物件定位的目標是將影像中的 2D 偵測結果轉換為 3D 世界座標，使系統能知道目標物在場景中的實際位置，並將此資訊提供給後續的目標確認、導航點產生與移動抓取流程。本研究在空間中放置四台相機以獲得多視角的相機畫面來進行物體定位。首先，系統在各個相機的 RGB 影像中執行 YOLO object detection，取得物體類別與 bounding box。對每一個 bounding box，系統取其中心點作為該相機觀察到的目標影像位置，並根據該相機的內參與外參建立投影關係，將 2D bbox center 反投影為一條由相機中心出發的 3D ray。

由於單一 RGB 相機只能知道物體「在哪個方向」，但不知道物體「離相機多遠」，因此無法只靠一張影像得到完整的 3D 位置。此系統利用多台相機從不同角度觀察同一個物體。每台相機都會根據影像中的 bounding box 中心點，推算出一條從相機出發、指向物體方向的 3D ray。當多台相機都看到同一類物體時，系統會把這些 3D rays 放在一起比較。如果多條 rays 在空間中指向相近的位置，就代表它們很可能是在看同一個物體；如果差太多，則可能是偵測錯誤或不同 instance。系統會先把可能屬於同一物體的 rays 分成同一群，再計算這些 rays 最接近的交會位置。這個交會位置就被視為該物體在世界座標中的位置。

為了提升定位結果的可靠性，系統在求得候選 3D 位置後，會將該位置重新投影回來源相機影像，並檢查投影點是否落在原始 bounding box 附近。只有通過此 reprojection consistency check 的候選點才會被保留。若多個候選點在 3D 空間中距離過近，系統會將其合併，以避免同一物體被重複輸出。接著，定位結果會交由 tracking 模組處理，根據 3D 空間距離與時間連續性維持穩定的 instance id，降低 YOLO 偵測抖動、短暫漏偵與多個同類物體造成的 instance 混淆。最後，系統將定位結果作為後續目標確認、候選導航點產生與移動抓取流程的輸入。

\subsubsection{Point Cloud}

Point cloud 是由大量三維座標點組成的資料形式，可用來表示物體表面、場景結構與空間幾何關係。相較於 2D image，point cloud 保留了每個點在三維空間中的位置，因此常被用於 3D perception、物體幾何分析與機器人操作等任務。在 RGB-D camera 中，point cloud 可由 RGB image 與 depth image 產生；其中 depth image 提供影像中每個像素對應的深度值，而 camera intrinsic 則提供焦距與主點位置。根據 pinhole camera model，每個 depth pixel 可由其像素座標與深度值反投影為 camera frame 下的 3D point，進而將影像平面上的資訊轉換為三維空間資料。

\subsection{Grasp Planning and Mobile Manipulation}

\subsubsection{Inverse Kinematics}

Inverse Kinematics（IK）是機械手臂控制中的基礎問題，其目標是在已知 end-effector 期望位置與姿態的情況下，求解一組可使機械手臂到達該目標 pose 的 joint angles。相對於 Forward Kinematics 由已知關節角度計算 end-effector pose，Inverse Kinematics 則是反向由目標 pose 推回關節配置。由於機械手臂通常具有多個自由度，且關節角度會受到機構限制、工作空間、奇異點與碰撞條件影響，因此 IK 不一定具有唯一解，也可能在目標超出工作空間時無解。實際機器人系統常使用解析式方法、數值迭代方法或最佳化方法求解 IK，並根據關節限制、姿態誤差與任務需求選擇合適解。對抓取任務而言，IK 可用來判斷候選抓取姿態是否能被手臂實際執行，因此是從 grasp pose 轉換到低階關節控制的重要步驟。

\subsubsection{PyBullet}

PyBullet 是 Bullet Physics SDK 的 Python 介面，常用於機器人模擬、物理運算與強化學習環境 \cite{pybullet}。透過 PyBullet，使用者可以載入 URDF、SDF 或 MJCF 等機器人模型與場景物件，並在模擬環境中進行剛體動力學、關節控制、forward kinematics、inverse kinematics 與 collision detection 等操作。對機器人操作任務而言，PyBullet 的價值在於能在實際執行前先檢查候選姿態是否可達、是否會與場景或機器人本體發生碰撞，並以較低成本驗證動作的幾何可行性。因此，PyBullet 常被用作機器人控制與抓取規劃中的模擬與安全檢查工具。

\subsubsection{GraspGen for Grasp Pose Generation}

Grasp pose generation 是機器人抓取任務中的核心問題，其目標是在已知物體或場景幾何資訊的情況下，產生機械手臂末端夾爪可執行的抓取姿態。對平行夾爪或吸盤式夾爪而言，一個 grasp pose 通常需要同時決定夾爪在三維空間中的位置與方向，因此屬於 6-DoF grasping 問題。相較於只在影像平面上預測抓取矩形的 2D grasp detection，6-DoF grasp pose generation 能直接描述夾爪在三維空間中的 approach direction、rotation 與 contact configuration，較適合用於機械手臂在真實三維場景中的抓取規劃。

GraspGen 是 Murali et al. 提出的 diffusion-based 6-DoF grasping framework，目標是在不同物體、不同夾爪形式與不同觀察完整度下產生可執行的抓取姿態 \cite{graspgen}。該模型將 grasp generation 視為一個迭代式 diffusion process，並以 3D point cloud 作為幾何輸入，產生多個候選 6-DoF grasp poses。其架構包含 Diffusion-Transformer grasp generator 與 discriminator：generator 負責從物體或場景點雲中取樣候選抓取姿態，discriminator 則負責對生成的 grasp poses 進行評分與過濾。透過此設計，GraspGen 不只輸出單一抓取結果，而是提供一組候選抓取姿態，使後續系統能依照碰撞、可達性與任務條件進一步篩選。

GraspGen 的另一個重點是 on-generator training。傳統 grasp discriminator 若只在離線資料集中的正負樣本上訓練，可能無法有效辨識 generator 實際產生的錯誤樣本。GraspGen 因此在 generator 所產生的 grasps 上訓練 discriminator，使評分模型更貼近生成器在推論時會產生的候選分布。為了提升模型的泛化能力，作者也建立大規模 simulated grasp dataset，涵蓋多種物件與夾爪形式，使模型能支援不同 gripper embodiments、partial 或 complete point clouds，以及 single-object 或 cluttered scenes。

對機器人操作而言，GraspGen 的價值在於將目標物的 3D 幾何資訊轉換為多個可排序的 6-DoF grasp candidates。這些候選姿態可以作為後續 inverse kinematics、collision checking 與 motion planning 的輸入。然而，GraspGen 輸出的候選 grasp pose 並不代表一定能被特定機械手臂直接執行；最終抓取動作仍需結合機器人工作空間、關節限制、底盤位置、障礙物分布與碰撞檢查進行驗證。因此，GraspGen 較適合作為 grasp candidate generator，負責產生多樣且具有幾何合理性的抓取候選，再由機器人系統根據實際控制限制選擇可執行解。

\section{Method}

\subsection{Overview}

\subsubsection{System Overview}

本章說明本研究如何將使用者的自然語言請求轉換為可執行的移動抓取任務。整體系統建立於 Unity 數位孿生環境中，並以 LangGraph 管理任務流程，以 A2A（Agent-to-Agent）協議整合需要較高運算資源的推論服務。系統將任務拆解為多個具有明確功能的 agents，分別負責任務分類、目標物鎖定、候選導航點產生、導航、VLM 決策、抓取姿態生成、車體接近、手臂執行與執行歷程記錄。部分流程依照預先定義的任務邏輯執行，而在需要根據車載影像與任務狀態判斷下一步行為時，系統則由 VLM 在有限的 agent action set 中選擇下一個應被呼叫的功能模組。ROS2 則位於數位孿生環境與控制流程之間，負責感測器資料傳輸、導航任務執行，以及將控制命令傳送至 Unity 中的車輪與機械手臂，使 agent workflow 的決策能轉換為數位孿生環境中的實際機器人動作。

為了使機器人能取得整體居家場景資訊，本研究在環境中架設多台環境相機，作為全域感知來源。系統透過這些相機觀察房間中的可抓取物件，並結合 YOLO 偵測結果、相機標定資訊與多視角幾何，估計物體在世界座標中的位置。此設計使機器人即使尚未從車載相機看到目標物，也能先根據環境相機取得目標物的大致位置、Size Dimension 與候選導航點。相對地，安裝於機械手臂上的第一人稱相機則負責近距離觀察。當機器人導航至目標附近後，第一人稱相機會提供當前視角下的即時影像，使 VLM 能判斷目標物是否清楚可見、是否受到遮擋，以及目前位置是否適合進入抓取流程。除此之外，第一人稱相機也能提供更近距離的目標物影像與深度資訊，作為後續目標確認、抓取姿態生成與手臂執行前幾何判斷的重要依據。

整體任務由使用者輸入開始。系統首先透過 task classifier 判斷輸入屬於 general chat 或 specific robot task。若輸入只是一般對話，系統會進入 general chat 分支並產生回覆，不會觸發機器人控制流程；若輸入為具體機器人任務，則進入 pick workflow。進入 pick workflow 後，系統會根據使用者請求與目前場景中的物體資訊鎖定 target instance。若場景中存在多個同類物體，系統需進一步確認使用者欲操作的實際目標，以避免自然語言描述造成的歧義。

目標物鎖定後，系統會呼叫 Size Dimension 估計 agent，根據多相機定位結果、目標物影像資訊、Size Dimension、地圖可行性與抓取需求，產生多個可供 Nav2 使用的候選 goal\_poses。這些候選點會被排序為 ranked goal\_poses，使系統能優先嘗試較適合觀察與抓取的位置。當候選 goal\_pose 被選定後，導航模組會透過 ROS2/Nav2 執行移動任務。機器人抵達目標附近後，系統再由第一人稱相機取得近距離觀察，並將影像、導航結果、目標資訊與執行歷程提供給 VLM。VLM 會在有限的 agent action set 中選擇下一步，例如進入抓取姿態生成、切換至下一個導航候選點、執行車體接近與手臂抓取，或結束任務。

整個 workflow 透過一份共同維護的任務狀態串接各 agents。每個 agent 會讀取目前任務中與自身相關的資訊，執行完成後將結果寫回狀態中，使後續節點能接續使用前一階段的輸出。若任務過程中發生目標移動、目標遺失、導航失敗、觀察不足、抓取失敗或接近失敗，workflow 會依據目前狀態進入重新估計、候選點切換、執行歷程記錄或返航流程。透過 LangGraph 的節點與條件路由，本研究能將自然語言任務轉換為可追蹤、可重試且具備失敗回復能力的移動抓取流程。

形式化而言，令使用者在時間 $t$ 的輸入為 $u_t$，任務分類器輸出 $c_t$ 為一般對話或具體機器人任務，分類可寫成
\begin{equation}
    c_t=\arg\max_{c\in\{\textsc{General},\textsc{Specific}\}}p_\theta(c\mid u_t,\mathcal{O}),
\end{equation}
其中 $\mathcal{O}$ 為目前可抓取物件清單與其別名資訊；若模型或外部服務不可用，系統仍保留以關鍵動詞與物件名稱為基礎的 fallback 判斷。整體 pick workflow 可視為共享任務狀態上的狀態轉移過程，第 $i$ 個 agent 只讀取與自身相關的部分狀態，產生局部更新後寫回共享狀態：
\begin{equation}
    s_{t+1}=F_i(s_t)=s_t\oplus \Delta_i, \qquad \Delta_i=f_i(P_i(s_t)),
\end{equation}
其中 $P_i(\cdot)$ 為 agent 對共享狀態的投影，$f_i$ 為該 agent 的感知、推理或控制函式，$\oplus$ 表示將更新合併回任務狀態。

\begin{algorithmblock}{System-level task routing}
\item Receive the user utterance and append it to the dialogue state.
\item Classify the utterance as general chat or a specific robot task.
\item If the utterance is general chat, generate a conversational reply and store the chat turn.
\item If the utterance is a specific task, resolve the target object and initialize the pick workflow.
\item During the pick workflow, keep updating the shared task state after every agent execution.
\item Terminate the workflow when the task succeeds, the user exits, or no feasible recovery remains.
\end{algorithmblock}

此外，系統在輸入端同時支援一般對話與機器人任務：對話開始時由 greeting\_node 向使用者問候並進入等待，使用者輸入後 human\_reply\_node 接收訊息並交由 task\_classification\_node 判斷其屬於 general chat 或 specific robot task。若為一般對話（例如問候、閒聊或詢問系統狀態），系統會進入 general chat 分支，由 ai\_reply\_node 產生自然語言回覆、chat\_memory\_node 記錄該輪對話以維持上下文，再回到 human\_reply\_node 等待下一次輸入，此分支不會觸發物體定位、導航與抓取等機器人控制流程；若使用者結束對話，則由 goodbye\_node 產生結束回覆並結束 session。只有當輸入被判定為 specific robot task 時，系統才會進入下節說明的 pick workflow。

\subsubsection{Specific Robot Task}

當 Task Classifier 判斷使用者輸入屬於 specific robot task 時，系統會將該輸入導向機器人任務分支。本研究目前以 pick task 作為主要任務情境，也就是使用者以自然語言要求機器人拿取指定物體。與 general chat 不同，specific robot task 不只是產生文字回覆，而是會啟動後續的 agents workflow，將使用者請求逐步轉換為可由機器人執行的任務流程。

進入 specific robot task 後，系統首先會解析使用者請求中的目標描述，並根據目前場景資訊尋找符合需求的目標物。若場景中只有一個符合條件的物體，系統可直接將其作為任務目標；若存在多個同類物體，系統則需進一步確認使用者欲操作的實際目標，以避免自然語言描述造成的歧義。目標確認完成後，workflow 會接續呼叫對應 agents 取得 Size Dimension，並產生可供機器人導航與觀察的候選位置。

接著，系統會根據候選位置安排導航任務，使機器人移動至目標附近。當機器人抵達候選位置後，系統會取得第一人稱相機的近距離觀察影像，並將目前影像、導航結果、目標資訊與任務狀態提供給 VLM 進行下一步決策。VLM 會在有限的 agent action set 中選擇下一個流程方向，例如繼續進入抓取流程、切換至其他候選位置重新觀察，或在任務完成與無法繼續時進入結束流程。

在任務執行過程中，workflow 會持續更新執行歷程，記錄目前嘗試過的候選位置、VLM 決策、導航結果、觀察狀態、抓取結果與失敗原因。這些紀錄不只用於保存執行歷史，也會作為後續決策的依據，使系統能避免在相同條件下重複嘗試已失敗的候選位置或動作。若目前候選位置無法完成任務，系統可根據執行歷程切換至下一個候選位置；若目標遺失或任務狀態已無法恢復，workflow 則會進入結束或返航流程。

當任務成功完成，或系統判斷無法繼續執行時，workflow 會進入任務收尾階段。此時系統會更新最終任務狀態，保存成功或失敗結果，並依照設定觸發 go home 流程，使機器人返回初始位置或指定 home pose。透過此設計，specific robot task 不只包含目標確認、導航、觀察與抓取，也包含任務過程中的執行歷程記錄與任務結束後的返回機制，使整體流程具備完整的開始、執行、恢復與收尾結構。整體流程可概括為
\begin{equation}
\begin{aligned}
    &\text{user request}
    \rightarrow \text{target instance}
    \rightarrow \text{object information} \\
    &\rightarrow \text{ranked goal\_poses}
    \rightarrow \text{navigation}
    \rightarrow \text{observation} \\
    &\rightarrow \text{VLM decision}
    \rightarrow \text{grasp or recovery}.
\end{aligned}
\end{equation}

\subsubsection{Workflow State and Communication Architecture}

本研究依據通訊對象與功能職責，將資料傳遞劃分為三個層次：LangGraph 負責主控流程的任務狀態管理與節點路由；A2A 作為主控流程向外部推論 agents 委派任務所依循的跨代理人通訊協定；ROS2 則銜接 Unity 數位孿生環境，承擔感測資料傳輸與機器人控制命令的收發。

\paragraph{LangGraph 任務狀態管理}
在主控流程內部，各節點並不直接互相傳遞訊息，而是透過共享的任務狀態進行協作。此狀態作為任務執行期間的全域紀錄，涵蓋使用者請求、目標物件、物體世界座標、候選導航點、導航結果、VLM 決策、抓取結果與車體接近結果等欄位。每個節點執行時僅讀取與自身功能相關的欄位，完成後僅回傳本次新增或修改的內容，由 LangGraph 將其合併回全域狀態，使前一節點的輸出自然成為後續節點的輸入，各節點無需彼此直接耦合。共享狀態可寫成
\begin{equation}
    s_t=\{u,q,o^\star,w_t,G_t,k_t,n_t,z_t,d_t,g_t,a_t,m_t\},
\end{equation}
其中 $u$ 為使用者請求，$q$ 為目標物描述，$o^\star$ 為鎖定的目標 instance，$w_t$ 為最新 world position data，$G_t=\{g^{(1)},\ldots,g^{(K)}\}$ 為候選導航點序列，$k_t$ 為目前嘗試的候選點 rank，$n_t$ 為導航結果，$z_t$ 為車載觀察，$d_t$ 為 VLM decision，$g_t$ 為 grasp result，$a_t$ 為 approach result，$m_t$ 為執行歷程。

以物件拾取任務為例：任務啟動後，系統依序將目標物件資訊、候選導航點、導航結果與相機觀察等內容寫入狀態，VLM 節點再根據當前狀態中的摘要欄位判斷後續動作，包含進入抓取及靠近流程、移往下一候選導航點重新觀察，或終止任務。若目標位置更新節點偵測到目標移動，系統才會重新整理 Size Dimension 與導航候選點。LangGraph 的作用因此不僅在於排定節點執行順序，更在於將每一步驟的結果系統性地保留為後續決策的依據。此目標移動判斷可寫成
\begin{equation}
    \lVert\hat{\mathbf{x}}^{\mathrm{new}}-\hat{\mathbf{x}}^{\mathrm{old}}\rVert_2>\tau_{\mathrm{move}}
    \quad\Rightarrow\quad
    s_{t+1}=F_{\mathrm{item\ info}}(s_t).
\end{equation}

任務狀態主要服務於單次任務執行期間的流程銜接。對話紀錄、任務摘要、執行歷史與成功／失敗結果等摘要性資訊會另行持久化至 session-scoped 資料庫，主要供流程追蹤、錯誤分析與實驗紀錄使用，而非作為後續 VLM 決策的直接輸入。原始影像與大量感測資料則僅作為當下推論或控制的即時輸入，不納入持久化紀錄，以控制狀態規模。

\paragraph{基於 A2A 協定的跨代理人協作}
對於運算量較高的推論任務，本研究將Size Dimension 估計與抓取姿態生成實作為符合 A2A 規範的獨立外部 agents。A2A 在本系統中是 HTTP-based agent communication；主控流程作為 client，透過 HTTP 通訊與 A2A SDK 呼叫遠端 agent server，在需要外部推論時向對應 agent 發派任務，將結構化資訊與影像資料一併傳送，並解析 agent 回傳的結構化結果後寫入任務狀態，供後續節點使用。值得注意的是，並非所有功能節點皆透過 A2A 運作；導航與車體接近控制主要透過本地流程與 ROS2 執行。此設計使外部推論 agents 得以獨立部署於不同執行環境或主機，並可在不影響整體 workflow 結構的前提下進行更新或替換。

\paragraph{ROS2 感測與控制通訊}
Unity 數位孿生環境中的感測資料與控制命令主要透過 ROS2 傳遞。系統透過 ROS2 接收來自 Unity 端的物體世界座標、相機影像、定位資訊、導航結果與手臂關節狀態，並透過 ROS2 發布導航目標與控制命令至移動底盤及機械手臂。ROS2 節點之間的 topic、service 與 action 通訊採用 ROS2 原生通訊機制完成；而 rosbridge websocket 則作為 Unity 或外部視覺化工具連接 ROS2 graph 的橋接介面，使非 ROS2 原生環境也能讀取或發布 ROS2 訊息。

\begin{algorithmblock}{Complete pick workflow}
\item Classify the user utterance. If it is general chat, answer conversationally and wait for the next utterance.
\item For a pick task, parse the requested object and read the latest world position data.
\item Lock the target instance. If multiple instances match, ask the user to select one using the candidate views.
\item Send the selected instance and room-camera evidence to the item-information agent.
\item Generate ranked goal\_poses and navigate to the highest-ranked feasible candidate.
\item Capture the car-camera observation and ask the VLM decision agent for the next high-level action.
\item If the decision is major navigation, refresh the target state and move to the next ranked goal\_pose.
\item If the decision is grasping, refresh the target state, generate grasp poses, and run base-arm approach.
\item Update memory after each navigation, decision, grasp, or approach result.
\item Return home after success, target loss, candidate exhaustion, or an unrecoverable failure.
\end{algorithmblock}

\subsubsection{目標物鎖定}

目標物鎖定的目的，是將使用者以自然語言描述的物體，對應到場景中實際存在的 target instance。由於使用者通常只會說出物體類別，例如「幫我拿杯子」或「幫我拿小熊」，系統必須先知道空間中有哪些可操作物體，以及這些物體在場景中的 3D 位置，才能進入後續導航與抓取流程。

在使用者提出任務前，系統會先透過多台環境相機取得空間中物體的 3D 座標資訊。本研究延續 Fang-Chen Hsu、Yi-Hsien Hsieh 與 Wen-Yu Su 於智慧家庭多相機感知與可觀測性模擬框架中的概念 \cite{hsu_multicam}，利用多台固定式環境相機從不同視角觀察同一居家場景，使系統能在機器人尚未接近目標物之前，先建立場景中可操作物體的空間資訊。各相機會偵測影像中的物體類別與影像位置，並根據相機標定資訊將影像中的物體位置轉換為空間中的觀察方向。由於單一 RGB 相機只能提供目標物相對於相機的方向，無法直接決定完整深度，因此系統會結合多台相機的觀察結果，透過多視角幾何估計物體在世界座標中的位置。最後，系統會為每個定位到的物體建立 instance 資訊，包含物體類別、instance id、世界座標、來源相機與對應影像區域，作為後續任務查詢與目標確認的依據。

當使用者輸入任務後，input\_node 會先從自然語言請求中解析出欲操作的物體類別。例如，若使用者說「幫我拿小熊」，系統會將任務目標解析為小熊；若使用者說「拿杯子給我」，則會將目標解析為杯子。此步驟只負責理解使用者想拿的物體類別，尚未決定場景中實際要操作的是哪一個 instance。接著，find\_node 會將解析出的物體類別與目前場景中的 3D 物體資訊進行比對，找出所有符合條件的候選物體。若場景中只有一個符合使用者請求的候選物體，系統會直接將其鎖定為本次任務的 target instance；若場景中存在多個同類物體，則需要根據物體位置、來源視角或使用者補充描述進一步確認實際目標。完成目標物鎖定後，系統會將選定的 target instance、物體世界座標與相關觀察資訊寫入任務狀態，作為後續任務的共同輸入。形式化而言，令目標描述為 $q$、場景候選集合為 $\mathcal{D}=\{d_1,\ldots,d_N\}$，符合條件的候選集合與被選定的目標 instance 為
\begin{equation}
    \mathcal{C}(q)=\left\{d_i\in\mathcal{D}\mid \operatorname{match}(q,d_i)=1\right\},
    \qquad
    o^{\star}=\begin{cases}
    \mathcal{C}(q)_1, & |\mathcal{C}(q)|=1,\\
    \operatorname{Confirm}(\mathcal{C}(q)), & |\mathcal{C}(q)|>1.
    \end{cases}
\end{equation}

在任務執行過程中，系統也會持續確認目標物是否仍存在於最新的場景資訊中。若目標物消失，或其位置與先前紀錄相差過大，代表目標可能已移動或感知結果需要更新，此時 workflow 會進入重新確認、重新估計或任務中止流程，降低後續導航與抓取流程操作錯誤物體的風險。

\subsubsection{Size Dimension and goal\_poses Selection}

目標物鎖定後，系統已取得 target instance 與其世界座標。然而，僅憑物體中心位置不足以支撐完整的移動抓取流程，物體尺寸與朝向會直接影響導航停靠點的選擇、抓取姿態的可行性、手臂可達性與碰撞檢查。因此，系統在導航前先估計目標物的幾何資訊，再根據候選抓取姿態與場景可通行空間產生 ranked goal\_poses。此流程由 get\_item\_info\_no\_sam3d\_node 觸發，該節點僅扮演 A2A client 的角色，負責整理目標資訊並發出請求；實際的Size Dimension 估計與候選 goal\_pose 生成則在 A2A server 端的 get\_item\_info\_agent\_no\_sam3d 完成，再將結果回傳寫入任務狀態。整體流程分為三個階段：Size Dimension 估計、GraspGen 抓取姿態生成，以及方向分群與候選導航點排序。

\paragraph{Size Dimension 估計}
Size Dimension 估計的目標是在不依賴深度感測的情況下，根據四台環境相機的 RGB 影像、相機標定資訊，以及前一階段取得的物體中心世界座標，將目標物近似為一個帶有 yaw 的 3D box。系統首先在各視角中以 YOLO 偵測目標物的 bounding box，並以該 bounding box 作為 SAM 的提示，取得目標物的 segmentation mask。若 SAM 在某一視角中未能產生有效結果，則以該視角的 bounding box 矩形區域作為近似遮罩，以維持Size Dimension 估計流程的穩定性。

物體高度由兩種幾何估計方式共同決定。第一種方式依據針孔相機模型，利用目標物在影像中的 bounding box 高度、相機焦距，以及物體中心相對於相機的深度，推算其真實高度。第二種方式則利用多視角觀察建立空間中的垂直參考線。具體而言，各相機中 bounding box 的中心點可形成一條由相機中心出發的觀察射線；系統先在水平面上求得最接近多條射線的物體中心位置，並以此建立穿過物體中心的垂直方向參考。接著，系統將各視角 bounding box 的上緣與下緣投影回此垂直參考線，得到另一組高度估計。最後，系統將上述兩種方法得到的有效高度候選值合併，並取其中位數作為基礎高度，以降低單一視角或單一估計方法造成的誤差。以針孔模型估計的高度為
\begin{equation}
    H^{\mathrm{bbox}}_i=\frac{h_i\,z_i}{f_{y,i}},
\end{equation}
其中 $h_i$ 為 bbox 像素高度，$f_{y,i}$ 為垂直焦距，$z_i$ 為物體中心在相機 $i$ 座標下的深度。垂直參考線由各相機觀察射線 $L_i(\mu)=C_i+\mu\mathbf{d}_i$ 在水平面上的最近交會點決定，等價於求解正規方程
\begin{equation}
    A\mathbf{x}=b,\quad
    A=\sum_i\left(I-\mathbf{d}_i\mathbf{d}_i^\top\right),\quad
    b=\sum_i\left(I-\mathbf{d}_i\mathbf{d}_i^\top\right)C_i,
\end{equation}
而基礎高度 $H_{\mathrm{ref}}$ 為有效 bbox 高度與垂直參考線高度的中位數。

水平尺寸則根據 SAM mask 的形狀比例估計。對每一個有效視角，系統會先依照相機與物體中心的相對位置，在影像平面上估計對應世界垂直方向與水平側向的投影軸。接著，系統將 mask 內的像素分別投影至這兩個軸上，並以 5\% 至 95\% 百分位範圍估計可見高度與可見寬度的像素尺度。此作法可避免 mask 邊界雜訊或少量離群點直接影響Size Dimension 估計。最後，系統以前述基礎高度作為比例尺，將影像中的可見寬度換算為真實空間中的水平寬度：
\begin{equation}
    W^{\mathrm{mask}}_i=H_{\mathrm{ref}}\,\frac{w^{\mathrm{mask}}_i}{h^{\mathrm{mask}}_i}.
\end{equation}

為了估計物體在地面上的 footprint 與 yaw，系統將物體底面近似為一個旋轉矩形，並以水平尺寸 $(s_x, s_z)$ 與朝向角 $\varphi$ 描述。對於方位角為 $\theta_i$ 的相機，該旋轉矩形在該視角下的預測可見寬度為：
\begin{equation}
    \hat{w}_i = \left|\sin(\theta_i - \varphi)\right|\,s_x + \left|\cos(\theta_i - \varphi)\right|\,s_z.
\end{equation}
系統會在 $\varphi \in [0, \pi]$ 的範圍內均勻搜尋可能的 yaw（預設 $721$ 個樣本），並在每一個候選 yaw 下，以最小二乘法估計對應的 $(s_x, s_z)$。最後，系統選擇使各視角預測寬度與實際估計寬度之間 RMSE 最小的結果，作為物體的水平尺寸與 yaw。為避免生成不合理的細長模型，系統會限制 footprint 的長寬比（預設上限 $1.8$）；若有效視角不足，則以各視角水平寬度的中位數作為 $s_x$ 與 $s_z$，並將 yaw 設為零。

取得基礎高度與水平尺寸後，系統會再依據物體形狀比例對高度進行縮放修正，以補償不同外形物體在幾何估計上的偏差。以 $\rho=H_{\mathrm{ref}}/(s_x+s_z)$ 為形狀比例，透過線性插值在錨點 $[0.70,1.03,2.28]\mapsto[0.65,0.80,0.90]$ 上查得權重 $w(\rho)$，最終輸出為物體尺寸 $\texttt{size\_xyz\_m} = [s_x,\, h,\, s_z]$ 與對應的 yaw，其中 $h=H_{\mathrm{ref}}\cdot w(\rho)\cdot\gamma$、$\gamma$ 為 height scale（預設 $1.0$）。

\begin{algorithmpseudo}{Geometric size estimation}
\begin{algorithmic}[1]
\Function{estimate\_object\_size}{object $o$, cameras $\mathcal{C}$}
  \ForAll{$c \in \mathcal{C}$ observing $o$}
    \State $M_c \gets$ \Call{sam}{image$_c$, bbox$_c$} \Comment{fallback: bbox rect}
  \EndFor
  \State $\ell_{xz} \gets$ \Call{fit\_vertical\_line}{$o,\ \mathcal{C}$} \Comment{$xz$ line via bbox rays}
  \ForAll{$c \in \mathcal{C}$ observing $o$}
    \State $H^{\mathrm{vl}}_c \gets$ project bbox top/bottom onto $\ell_{xz}$
    \State $H^{\mathrm{bbox}}_c \gets h_c\, z_c / f_{y,c}$ \Comment{pinhole bbox height}
  \EndFor
  \State $H_{\mathrm{ref}} \gets \operatorname{median}\big(\{H^{\mathrm{bbox}}_c\} \cup \{H^{\mathrm{vl}}\ \text{if valid}\}\big)$
  \ForAll{$c \in \mathcal{C}$ with mask $M_c$}
    \State $\mathbf{e}^x_c,\ \mathbf{e}^y_c \gets$ world side/up axes projected at $o$
    \State $w^{\mathrm{px}}_c,\ h^{\mathrm{px}}_c \gets$ 5--95\% extent of $M_c$ on $\mathbf{e}^x_c,\mathbf{e}^y_c$
    \State $W_c \gets H_{\mathrm{ref}} \cdot w^{\mathrm{px}}_c / h^{\mathrm{px}}_c$
  \EndFor
  \If{only one $W_c$ is available}
    \State $s_x \gets s_z \gets \operatorname{median}(W_c)$;\quad $\varphi^\star \gets 0$
  \Else
    \State $\theta_c \gets$ azimuth of each camera about $o$;\quad $r^\star \gets \infty$
    \For{$\varphi \in \operatorname{linspace}(0,\ \pi,\ 721)$}
      \State $B_c \gets \big[\lvert\sin(\theta_c-\varphi)\rvert,\ \lvert\cos(\theta_c-\varphi)\rvert\big]$
      \State $(s_x, s_z) \gets \arg\min_{s \ge 0} \lVert B\,s - W \rVert_2$ \Comment{lstsq}
      \State clamp $s_x,s_z$ to $\ge s_{\min}$, aspect $\le 1.8$
      \State $r \gets \operatorname{RMSE}(B\,[s_x, s_z]^\top,\ W)$
      \State \textbf{if} $r < r^\star$: $r^\star \gets r$, $\varphi^\star \gets \varphi$, keep $(s_x, s_z)$
    \EndFor
  \EndIf
  \State $\rho \gets H_{\mathrm{ref}} / (s_x + s_z)$ \Comment{shape ratio}
  \State $h \gets H_{\mathrm{ref}} \cdot w(\rho) \cdot \gamma$ \Comment{$w(\rho)$ shape weight; $\gamma$ height scale}
  \State \Return size $[s_x,\ h,\ s_z]$ and yaw $\varphi^\star$
\EndFunction
\end{algorithmic}
\end{algorithmpseudo}

\paragraph{GraspGen 夾取姿態生成}
完成Size Dimension 估計後，系統會將目標物轉換成 GraspGen 可使用的幾何輸入。由於 GraspGen 需要根據物體的三維形狀產生候選抓取姿態，因此本研究將前一階段估計出的物體中心、長寬高與 yaw 組合成一個 3D box approximation。此 3D box 代表目標物在世界座標中的大致佔據範圍；系統會從 box 表面或內部取樣幾何點，形成目標物的近似點雲，作為 GraspGen 的輸入。相同地，場景中的其他物體也會以其估計尺寸與位置建立 3D box approximation，作為後續判斷碰撞時的障礙物模型。box 內取樣的局部點 $p_{\mathrm{local}}$ 會套上 yaw 旋轉並平移至物體中心：
\begin{equation}
    R_\varphi=\begin{bmatrix} \cos\varphi & 0 & \sin\varphi\\ 0 & 1 & 0\\ -\sin\varphi & 0 & \cos\varphi\end{bmatrix},
    \qquad
    p_{\mathrm{world}}=R_\varphi\,p_{\mathrm{local}}+\hat{\mathbf{x}}.
\end{equation}

GraspGen 會根據目標物的近似點雲產生多個候選 6-DoF grasp poses。這些候選姿態描述夾爪可以從哪些位置與方向接近目標物，但它們仍只是物體局部幾何下的抓取候選，尚未考慮機器人目前所在位置、導航地圖、周圍障礙物與車體接近限制。因此，系統不會直接採用 GraspGen 的輸出作為最終動作，而是先將候選抓取姿態轉換到與導航地圖一致的座標表示，使抓取姿態、目標物位置、障礙物位置、導航地圖與機器人 pose 能在同一個空間中進行比較。

完成座標對齊後，系統會進行碰撞與可行性過濾。此步驟會檢查候選抓取姿態是否與目標物以外的障礙物 box 發生衝突，也會排除會使車體停靠位置落在不可通行區域的候選。只有通過碰撞檢查與空間可行性判斷的候選姿態，才會被保留下來，作為後續方向分群與 goal\_pose 排序的依據。

\paragraph{候選 goal\_pose 排序}
通過碰撞過濾的候選抓取姿態會進一步依據 approach direction 進行分群。本研究將水平面的接近方向劃分為八個 grasp orientation groups，每一群代表一個主要的車體接近角度。對於每一個候選抓取姿態，系統會根據其 approach direction 推算對應的車體停靠位置，並檢查該停靠位置的車體 footprint 是否落在 Occupancy Grid Map 的 free space 中。若車體 footprint 不與障礙物或 keepout 區域重疊，則該抓取姿態被視為可行姿態，並依其接近方向存入對應的 orientation group。令目標物中心為 $\hat{\mathbf{x}}$、接近方向為 $\mathbf{d}_m$、操作距離為 $\rho_m$，候選停靠點與其朝向為
\begin{equation}
    \mathbf{p}_m=\Pi_{xy}(\hat{\mathbf{x}}+\rho_m\mathbf{d}_m),\quad
    \psi_m=\operatorname{atan2}(\hat{y}-p_{m,y},\,\hat{x}-p_{m,x}),\quad
    \chi(g_m)=\mathbb{I}\!\left[\mathcal{B}(g_m)\subseteq\Omega_{\mathrm{free}}\right],
\end{equation}
其中 $g_m=(p_{m,x},p_{m,y},\psi_m)$，$\mathcal{B}(g_m)$ 為車體 footprint，$\Omega_{\mathrm{free}}$ 為可通行區域。

完成分群後，系統會根據各 group 的可行性進行排序。若某一方向群中保留的可行抓取姿態數量較多，代表該方向有較多可能的抓取方式；若該方向在碰撞過濾後仍保留較高比例的候選姿態，代表該方向較不容易受到周圍障礙物限制；若其對應的車體停靠位置也位於可通行區域，則表示該方向同時滿足抓取與導航需求。因此，系統會優先選擇可行姿態數量較多、碰撞過濾通過率較高，且對應車體停靠位置位於 free space 的方向群，作為 ranked goal\_poses 的排序依據：
\begin{equation}
    \operatorname{score}(r)=\left(n_r,\;\max_{m\in r}\beta_m,\;\chi(g_m)\right),
\end{equation}
其中 $n_r$ 為第 $r$ 群的可行候選數量，$\beta_m$ 為對應候選的 grasp 或 observation confidence。排序後的 $G=\{g^{(1)},\ldots,g^{(K)}\}$ 會寫入 navigation state。

\subsubsection{Nav2 FollowPath 改良}

在移動抓取流程中，導航的目標不只是讓機器人抵達目標物附近，而是要使機器人停在適合觀察與後續抓取的位置與朝向。pros 系統已能規劃路徑並驅動車體沿路抵達指定位置 \cite{yushiang2025}，然而原有流程主要以位置到達作為導航完成條件，未完整處理目標朝向。因此，即使車體成功移動至目標點，仍可能未面向目標物，導致安裝於機械手臂上的第一人稱相機無法取得正確觀察視角，進而影響後續的視覺判斷。為解決此問題，本研究對導航流程進行兩項改良。

\paragraph{朝向修正}
系統在產生候選停靠點時，會根據停靠點與目標物中心的相對位置計算車體應面向的方向，並將此朝向納入目標位姿。車體沿規劃路徑抵達終點、位置誤差進入容許範圍後，系統會進一步比對當前車體朝向與目標朝向之間的角度誤差，若誤差超出可接受範圍，則執行原地旋轉修正。由於原地旋轉本身會產生平移誤差，朝向修正完成後不再重新檢查位置誤差，而是以旋轉角度落入容許範圍作為導航成功的最終判定條件。若目標在 map frame 中位置為 $(x_o,y_o)$、候選停靠點為 $(x_g,y_g)$，則 goal yaw 為
\begin{equation}
    \psi_g=\operatorname{atan2}(y_o-y_g,\,x_o-x_g),
\end{equation}
車體沿全域路徑移動時，會選取距離車體至少 $d_{\min}=0.2$ m 的 local target point 並計算 heading error $e^{\ell}_t$，依角度誤差決定前進或左右旋轉；導航成功的最終條件為
\begin{equation}
    \lVert \mathbf{x}_t-\mathbf{x}_g\rVert_2\leq \tau_d
    \quad\text{and}\quad
    |\operatorname{wrap}(\psi_g-\theta_t)|\leq \tau_{\psi}.
\end{equation}

\paragraph{Keepout 區域限制}
佔用格網地圖（Occupancy Grid Map）記錄的可通行區域依賴感測器掃描結果，然而 LiDAR 在實際環境中存在掃描盲區。以桌子為例，LiDAR 通常只能掃到桌腳，桌面下方的空間在地圖上可能被標示為可通行，但車體實際上無法安全進入或停靠於此。本研究在導航地圖中額外加入 keepout 層，將這些因感測器盲區或任務需求而不適合車體通過或停靠的位置明確標記為限制區域，使路徑規劃在產生路徑與檢查停靠點時能主動迴避。對每一個候選停靠點 $g_m$，系統會檢查車體 footprint 是否完全位於 keepout map 的 free area：
\begin{equation}
    \chi_{\mathrm{keep}}(g_m)=\mathbb{I}\!\left[\mathcal{B}(g_m)\subseteq\Omega_{\mathrm{free}}^{\mathrm{keepout}}\right],
\end{equation}
只有 $\chi_{\mathrm{keep}}(g_m)=1$ 的候選點會被保留並排序；相同的 keepout map 也會在近距離車體接近階段再次使用。

\begin{algorithmblock}{Improved Nav2 FollowPath with keepout map}
\item Generate ranked goal\_poses from the selected target, grasp approach directions, and keepout-map feasibility.
\item Convert the selected goal\_pose to a ROS map pose whose yaw faces the target center.
\item Follow the Nav2 global path by selecting a local target point at least $0.2$ m from the robot.
\item Rotate when the heading error is too large; otherwise move forward, using slow actions near the final goal.
\item Switch to final yaw alignment near the goal and report success only when both distance and heading tolerances are satisfied.
\item If the goal is blocked by keepout map, navigation failure, or poor observation, update memory and switch to the next ranked goal\_pose.
\end{algorithmblock}

\subsubsection{VLM 決策}

當機器人完成 Nav2 導航並抵達目前候選 goal\_pose 後，系統會進入VLM 決策階段。前一階段的導航流程已使車體停在目標物附近，並讓車體朝向目標物。然而，從環境相機與候選導航點所得到的資訊仍屬於遠距離且較粗略的估計，無法完全保證目標物在近距離視角下清楚可見，也無法確認目前停靠點是否適合直接進入抓取。因此，本研究在進入抓取流程前，透過車載第一人稱相機取得近距離觀察，並由 VLM 根據當前影像與任務狀態選擇後續行動。

\paragraph{Observe node}
Observe node 的主要功能，是在車體抵達候選 goal\_pose 後取得第一人稱觀察影像。本研究的第一人稱相機安裝於機械手臂上，因此其視角接近機器人實際執行抓取前所能觀察到的畫面。相較於環境相機，車載第一人稱相機能提供更接近抓取階段的視覺資訊，適合用來確認目標物是否位於車體前方、是否出現在目前視野中、是否受到其他物體遮擋，以及目前停靠位置是否足以支援後續抓取姿態生成與車體接近流程。

在此節點中，系統會擷取車載 RGB 影像，並將其與目前 workflow state 一併整理為後續 VLM 決策的輸入。此狀態包含使用者請求、已鎖定的 target instance、目前候選 goal\_pose、導航結果、先前估計的目標物位置與尺寸，以及歷史執行紀錄。

\paragraph{Reason node}
Reason node 負責根據 observe node 取得的第一人稱影像與目前任務狀態，判斷下一步應呼叫哪一個 agent。系統會將目前影像、目標物描述、導航結果、候選點資訊與近期歷史紀錄整理成 prompt，使 VLM 判斷目前視角是否足以繼續任務。此判斷包含目標物是否出現在影像中、影像中的物體是否符合使用者指定目標、目標是否被遮擋、目前視角是否適合進入抓取流程，以及是否需要切換至下一個候選 goal\_pose 重新觀察。

為了避免 VLM 產生不可執行或不穩定的自由文字控制命令，本研究將 VLM 的輸出限制在預先定義的 agent action set 中。若 VLM 判斷目標物清楚可見，且目前視角足以支援後續抓取，workflow 會進入抓取姿態生成階段；若 VLM 判斷目標物未出現在畫面中、受到遮擋，或目前視角不適合抓取，workflow 則會切換至下一個 ranked goal\_pose，讓機器人從另一個方向重新導航與觀察。此決策可寫成在有限動作集合上的選擇
\begin{equation}
    \mathcal{A}=\{\textsc{MajorNav},\textsc{GraspPipeline},\textsc{Done}\},
    \qquad
    a_t=\arg\max_{a\in\mathcal{A}}p_{\phi}(a\mid\Phi(s_t,o_t,m_t)),
\end{equation}
其中 $o_t$ 為車載影像觀察，$m_t$ 為最近執行歷程，輸出以結構化 JSON 表示。

Reason node 的決策結果會被寫回 workflow state，包含 VLM 對目前影像的判斷、選擇的 agent action、失敗原因、已嘗試的候選點與後續流程方向。這些資訊會成為後續決策依據，使系統避免在相同候選點與相同視角下重複做出相同錯誤選擇。例如，若某個候選 goal\_pose 已被判定為目標不可見或遮擋嚴重，系統在後續重試時會降低該候選點的優先度，或直接切換至下一個候選方向。

\subsubsection{抓取pipeline}

當 reason node 判斷目前車載觀察已足以嘗試抓取時，workflow 會進入抓取 pipeline。本階段的目標，是將近距離 RGB-D 觀察轉換為可實際執行的車體接近與手臂抓取動作。雖然抓取流程內部包含目標狀態更新、抓取姿態生成、底盤接近、手臂執行與結果記錄等多個步驟，但本研究將其設計為一條連續 pipeline，而不是在每個子階段都重新呼叫 VLM 決策。其原因在於，當 VLM 已經根據車載影像與任務狀態判斷目前視角適合進入抓取後，後續問題主要轉為幾何估計、點雲處理、碰撞檢查、IK 可達性判斷與低階控制執行。這些步驟的輸入與輸出相對明確，若每個階段都再次要求 VLM 推論，不僅會增加推論時間，也可能在原本可由規則與幾何檢查完成的流程中引入不必要的不確定性。

進入抓取 pipeline 後，workflow 會依序執行 \texttt{update\_\allowbreak item\_\allowbreak info\_\allowbreak node}、\texttt{car\_\allowbreak grasp\_\allowbreak node}、\texttt{car\_\allowbreak approach\_\allowbreak node}，並在失敗時進入 \texttt{update\_\allowbreak memory\_\allowbreak node} 記錄結果。若 \texttt{car\_\allowbreak approach\_\allowbreak node} 成功完成抓取，workflow 會直接進入任務收尾與返航流程；若抓取姿態生成或車體接近失敗，系統才會更新執行歷程，並回到後續觀察與決策迴圈，使 VLM 根據失敗原因判斷是否切換至下一個候選導航點。此 pipeline 可表示為
\begin{equation}
    \textsc{GraspPipeline}:
    s_t \xrightarrow{\mathrm{update}} s_t'
    \xrightarrow{\mathrm{grasp}} g_t
    \xrightarrow{\mathrm{approach}} a_t
    \xrightarrow{\mathrm{memory}} m_{t+1}.
\end{equation}

\paragraph{update\_item\_info\_node}
update\_item\_info\_node 是抓取 pipeline 的入口，此節點的設計目的，是在抓取前加入一次狀態一致性檢查。它避免系統因為目標位置變化，而對錯誤物體或過期位置執行抓取。同時，這也讓抓取 pipeline 在真正進入低階控制前，仍保留重新估計與安全退出的能力。

此節點會更新目標物座標資訊，若目標物已不存在於最新觀察中，系統會清空當前導航與抓取相關狀態，並進入任務結束或返航流程。若目標仍存在，但最新位置與先前估計位置的差距超過門檻，代表目標物可能已移動，系統會回到Size Dimension 估計流程，重新估計 Size Dimension 與 ranked goal\_poses。只有當目標物仍存在，且位置變化仍在可接受範圍內時，workflow 才會將更新後的目標狀態寫回任務狀態，並繼續進入 car\_grasp\_node。其判斷可寫成
\begin{equation}
    \delta_t=\left\lVert \hat{\mathbf{x}}^{\mathrm{new}}_t-\hat{\mathbf{x}}^{\mathrm{old}}_t\right\rVert_2,
    \qquad
    \delta_t>\tau_{\mathrm{move}} \Rightarrow \textsc{ReEstimateItemInfo}.
\end{equation}

\paragraph{car\_grasp\_node}
car\_grasp\_node 負責根據車載第一人稱相機的近距離觀察產生候選抓取姿態。在 workflow 中，car\_grasp\_node 是抓取 pipeline 的其中一個節點；在系統實作上，它扮演 A2A client 的角色，負責將目前任務狀態與車載觀察資料送至外部 grasp agent。這樣設計的原因在於，GraspGen、影像分割、點雲建立與候選抓取姿態生成需要較高的運算資源，因此本研究將此類推論服務獨立為 A2A agent，使主控流程不需要直接處理模型內部推論細節，只需以標準化資料呼叫服務並接收回傳結果。

進入 car\_grasp\_node 後，系統會整理車載 RGB 影像、深度影像、目前機器人定位資訊、目標物描述、target instance 與最新目標物資訊，並透過 A2A request 傳送給外部 grasp agent。grasp agent 接收資料後，會在車載 RGB 影像中確認目標物，並以目標 bounding box 取得 segmentation mask。接著，系統將 mask 與 depth map 對齊，根據相機內參把目標物區域的深度像素回投影為 target point cloud；同時，非目標區域的有效深度點會形成 scene point cloud，作為周圍環境與障礙物的表示。其回投影與目標點雲集合為
\begin{equation}
    X=\frac{(u-c_x)Z(u,v)}{f_x},\;
    Y=\frac{(v-c_y)Z(u,v)}{f_y},\;
    Z=Z(u,v),
\end{equation}
\begin{equation}
    \mathcal{P}_{\mathrm{obj}}=
    \left\{(X,Y,Z)\mid M(u,v)=1,\;Z_{\min}<Z(u,v)<Z_{\max}\right\},
\end{equation}
其中 $M(u,v)$ 為目標 mask。

建立點雲後，grasp agent 會先移除無效或不合理深度點，並對點雲進行降採樣，將 target point cloud 與 scene point cloud 輸入 GraspGen，產生多個候選 6-DoF grasp poses，並透過 collision filtering 移除會與周圍場景衝突的姿態。最後，grasp agent 會將有效候選姿態與相關偵測資訊回傳給 car\_grasp\_node，由 car\_grasp\_node 將 grasp result 寫回 workflow state，作為後續 car\_approach\_node 的輸入。有效候選姿態 $\mathcal{R}=\{(T_m,\beta_m)\}$（$T_m\in SE(3)$、$\beta_m$ 為 grasp confidence）的排序不只看 confidence，而是先依 grasp position 與目前 gripper midpoint 的距離排序，再以 confidence 作為次要準則：
\begin{equation}
    \kappa_m=\left(\left\lVert \mathbf{t}_m-\mathbf{p}_{\mathrm{gripper}}\right\rVert_2,\;-\beta_m\right).
\end{equation}

\begin{algorithmblock}{Grasp pose generation in the grasp agent}
\item Receive RGB-D, AMCL pose, object id, target instance, and world center through an A2A request.
\item Detect the target with YOLO and obtain a SAM mask from the chosen bounding box.
\item Align the mask with the depth map and back-project target pixels into a target point cloud; non-target pixels form the scene point cloud.
\item Filter invalid depth, downsample, and run GraspGen with collision filtering.
\item Rank valid grasp poses by gripper-midpoint distance and confidence, and return them to \texttt{car\_grasp\_node}.
\end{algorithmblock}

\paragraph{car\_approach\_node}
car\_approach\_node 是抓取 pipeline 中將候選 grasp pose 轉換為實際底盤與手臂動作的節點。即使 car\_grasp\_node 已產生可行的抓取姿態，車體仍需要更接近目標物，找到一個能讓手臂到達該姿態、且車體不會碰撞的底盤位置。因此，此節點不會直接執行手臂抓取，而是先根據 grasp pose、目標物位置、機器人目前 pose 與場景障礙物，搜尋可執行的抓取策略。

在微調車體位置階段，系統會根據 grasp approach direction，在目標物周圍產生多個候選底盤 pose。每個候選 pose 都需要通過三類檢查。第一是地圖可行性檢查：系統會檢查候選底盤 pose 對應的車體 footprint 是否位於 keepout map 的 free space，並避免進入不適合停靠區域。第二是碰撞檢查：底盤、手臂與夾爪接近方向不能與場景障礙物或目標物以外的物體發生碰撞。第三是 IK 可達性檢查：手臂必須能從該底盤 pose 到達指定 grasp pose，且末端位置與姿態誤差需落在可接受範圍內。可行解選擇可表示為
\begin{equation}
    b^{\star}=\arg\min_{b\in\mathcal{B}}J(b,T_m)
    \quad\text{s.t.}\quad
    b\in\Omega_{\mathrm{free}},\;
    \operatorname{CollisionFree}(b,T_m)=1,\;
    \operatorname{IK}(b,T_m)=1.
\end{equation}

若系統找到同時滿足地圖可行、無碰撞與 IK 可達的底盤解，該解會被選為 selected base pose，並進入實際執行階段。若系統沒有找到完全滿足 IK 條件的可行解，但存在不碰撞且距離目標較近的候選底盤位置，則會將其記錄為 closest solution，作為後續執行或 fallback 判斷的參考。這樣設計的原因在於，GraspGen 產生的 grasp pose 只是眾多可能抓取姿態中的候選之一，實際抓取並不必然只能精確執行該姿態。對於同一個物體而言，夾爪的接近方向、末端位置與底盤停靠點可能存在多個近似可行解；即使某些候選姿態無法完全通過 IK 求解，只要車體位置不與環境碰撞，且手臂末端與目標之間的誤差仍在可接受範圍內，系統仍可能透過後續車體微調或手臂控制完成抓取。

在實際執行階段，車體移動至 selected base pose 後，系統會根據實際 AMCL pose 重新計算目標物相對於機器人底座的位置，再進行 IK 求解。這樣做是為了補償車體導航時產生的定位誤差，避免手臂仍依照導航前假設的位置執行，導致夾爪對不準目標。夾取完畢後，無論抓取成功或失敗，car\_approach\_node 都會使手臂回到 reset joints，並讓車體返回接近前的位置或安全狀態。最後，此節點會回傳 selected solution、closest solution、取樣摘要、車體導航結果、手臂執行結果、車體返回結果與失敗階段。透過這些資訊，上層 workflow 可以判斷失敗發生在哪個確切的階段，而不是只得到一個模糊的失敗訊號。

\begin{algorithmblock}{Base-arm approach}
\item Sample base poses around the target along the grasp approach direction for each valid grasp pose.
\item Reject candidates whose footprint leaves the keepout-map free space, that collide, or that fail IK reachability.
\item Select the executable base pose; if none is fully feasible, keep the closest collision-free pose as a fallback.
\item Drive the base to the selected pose, recompute arm compensation from the actual AMCL pose, and run the arm grasp sequence.
\item Reset the arm and return the base, then report the selected/closest solution, per-stage results, and failure phase.
\end{algorithmblock}

\paragraph{major\_nav\_node}

在 pick workflow 中，系統不假設第一個候選 goal\_pose 一定能完成任務。若機器人抵達目前候選點後，車載相機觀察結果不佳，例如目標物未出現在畫面中、受到遮擋，或 VLM 判斷目前視角不適合進入抓取流程，系統便會切換至下一個候選 goal\_pose。

此流程由 major\_nav\_node 負責。major\_nav\_node 會從 ranked goal\_poses 中選取下一個尚未嘗試的候選點，並將其更新為新的 navigation goal。接著，workflow 會再次呼叫 nav\_move\_node，使機器人依照新的 goal\_pose 導航至下一個停靠位置。令排序後的候選點為 $G=\{g^{(1)},\ldots,g^{(K)}\}$、目前嘗試第 $k$ 個，則切換更新為 $k\leftarrow k+1,\; g_t\leftarrow g^{(k)}$。

當機器人抵達新的候選點後，系統會再次進入 observe node，擷取新的第一人稱影像，並交由 reason node 判斷是否可以進入抓取 pipeline。若新的視角仍不可行，系統會繼續切換至下一個候選點；若所有候選點皆已嘗試完畢，workflow 則會將任務標記為無可行觀察位置，並由 nav\_home\_node 進入任務結束與返航流程。

\subsubsection{執行歷程記錄}

在本研究的 pick workflow 中，update\_memory\_node 的目的是將最近一次導航、觀察或抓取嘗試整理成下一輪決策可用的執行歷程摘要。由於任務可能經歷多次候選點切換與抓取嘗試，若系統不記錄先前結果，就可能在相同視角或相同失敗條件下重複執行相同動作。因此，update\_memory\_node 會將最近一次執行的 action、VLM reasoning、執行結果、成功與否，以及關鍵失敗資訊整理後寫入 history buffer，並供後續 reason node 建立 prompt 時使用。執行歷程可表示為有界歷史序列
\begin{equation}
    m_{t+1}=\operatorname{Keep}_{K}\left(m_t\cup\{(a_t,r_t,e_t,\eta_t)\}\right),
\end{equation}
其中 $a_t$ 為高層動作，$r_t$ 為決策原因或節點摘要，$e_t$ 為執行結果，$\eta_t$ 為關鍵事實。

執行歷程記錄後，reason node 在建立 VLM prompt 時會取最近幾筆 history buffer，放入 Recent Action History。VLM 因此能看到最近執行過哪些 action、結果是否成功，以及 key facts 中的關鍵失敗資訊。例如，若上一輪 car\_approach\_node 的 key facts 顯示 approach\_success=false 或 arm\_success=false，VLM 便能知道目前候選點下的抓取執行並不理想，進而傾向切換至下一個候選 goal\_pose，而不是重複相同抓取流程。



\section{Experiments}

本章說明本研究之實驗環境、執行平台、模型設定、消融設計與實驗結果。第四章的重點不是單獨評估某一個感知或控制模組，而是驗證第三章提出的 workflow 是否能在完整閉環中完成自然語言指定的移動抓取任務。因此，本章先介紹 Unity 數位孿生場景與機器人配置，再說明 workflow 執行機器與模型選用，最後以 A0--A3 消融實驗分析各核心設計對任務成功率、任務時間與失敗模式的影響。

\subsection{Unity 場景}

本研究於 Unity 數位孿生環境中進行實驗。場景採用自建居家空間，包含客廳家具、可抓取物件、移動機器人、車載相機、環境相機、Nav2 導航地圖與 keepout map。Unity 端負責提供可重複測試的室內場景與影像觀測，ROS2 端則負責導航、控制與狀態回傳，使每次 trial 可在相同地圖與物件配置下比較不同 workflow 設計的差異。

\subsubsection{虛擬車}

本研究使用的虛擬車延續既有 PROS 數位孿生平台之機器人建模流程。該論文以 Fusion 360 建立與實體機構一致的機器人 CAD model，並將模型匯出為 XACRO/URDF 後匯入 Unity；同時在 Fusion 360 中設定各關節的角度上下限與 joint type，使虛擬模型能反映實體機構的運動限制並降低模擬自碰撞風險 \cite{yushiang2025}。本研究沿用此類建模概念，將車體、五自由度手臂與夾爪以 URDF/mesh 方式納入 Unity 與 ROS2 控制流程，使導航、手臂關節限制與後續 PyBullet 可達性檢查能使用一致的機器人幾何設定。

在實驗設定中，車體可通行性檢查使用的底盤尺寸為 $0.35\,\mathrm{m}\times0.33\,\mathrm{m}$。手臂與夾爪控制採五個 controllable joints，其角度限制如表~\ref{tab:virtual-car-joint-limits} 所示。這些限制會在 car approach 階段用於判斷候選底盤位置是否能形成可達且不碰撞的抓取姿態。換言之，虛擬車不只是可視化模型，而是同時參與導航可行性、手臂可達性與實驗成功判定的幾何基礎。

\subsection{Workflow 執行平台}

\subsubsection{系統部署與運算平台}

本研究採三機分散式部署方式執行完整 workflow，將即時控制、數位孿生模擬、語意推論與高成本的幾何/抓取推論分離，使各模組能在較適合的硬體上執行。以下分別說明三個運算平台的硬體配置、執行內容與部署考量。

第一個平台負責需要較高運算資源的幾何與抓取推論，相關服務部署在 NVIDIA GeForce RTX 3090 的運算平台上。此平台以 A2A server 形式提供Size Dimension 估計與抓取姿態生成服務，集中執行 \texttt{get\_item\_info\_agent\_no\_sam3d} 與 \texttt{grasp\_agent}，並輸出 Size Dimension、ranked goal\_poses 與 6-DoF grasp pose。將此類高成本推論集中於獨立平台，可避免主控端承擔大型模型與抓取生成所需的運算負載。

第二個平台負責語意推論，相關 VLM/LLM 服務部署在 Mac mini M4 Pro 上，並透過 Ollama 提供 task classifier、general chat 與 reason node 所需之模型推論服務。

第三個平台為系統主控平台，主要 workflow 與即時控制流程部署在 AMD Ryzen AI 7 350 平台上，負責上述幾何／抓取推論與語意推論服務以外的流程，包含 Unity 數位孿生環境、ROS2/Nav2 導航控制，以及與感測、定位和機器人控制緊密相關的模組。

所有實驗皆使用上述相同部署設定，因此不同條件之間的差異主要來自 workflow 設計，而非運算平台或模型服務部署差異。
\subsubsection{模型選用}

本研究實驗主流程使用的模型可分為高層語意決策、物件偵測與分割、Size Dimension 估計、抓取姿態生成四類，以下依模組分別說明從程式與設定檔中可確認的模型、版本與用途。為避免混淆，本章只將 A0--A3 主流程實際呼叫的 no-SAM3D item-info 與 grasp agent 列為實驗模型；legacy SAM3D/full 3D pipeline 雖仍保留於程式庫中，但未納入本章消融結果分析。

\begin{itemize}
  \item \textbf{Ollama}：高層語意決策與對話相關之模型皆透過 Ollama 的 OpenAI-compatible API 提供。其中，車載影像觀察後的 VLM reason node 與一般聊天對話皆使用 \texttt{gemma3:12b}；task classifier 則使用 \texttt{qwen2.5-coder:3b}，用於判斷使用者輸入屬於 general chat 或 specific robot task。
  \item \textbf{YOLO}：目標物偵測模型採用 Ultralytics YOLO26~\cite{ultralytics_yolo}，並以 Roboflow 平台進行訓練。訓練時使用 Train from COCO Pretrained Weights 設定，使模型以 COCO 預訓練權重作為初始化，再針對本研究所需之居家物件資料集進行微調。訓練完成後，模型在 valid set 上的偵測表現如表~\ref{tab:yolo-metrics} 所示。
  \item \textbf{SAM}：影像分割模型採用 Segment Anything Model（SAM）~\cite{sam}，並使用 ViT-Base backbone 進行 bounding box prompt segmentation。系統會將 YOLO 偵測到的 bounding box 作為 SAM 的 prompt，進一步產生目標物 mask。
  \item \textbf{GraspGen}：抓取姿態生成採用 GraspGen runtime~\cite{graspgen}，根據 target point cloud 與 scene point cloud 產生多組 6-DoF grasp candidates，並透過 collision filtering 移除可能與場景碰撞的候選姿態。實驗中每次取樣 800 個 grasp candidates，並保留前 400 個候選進行後續篩選。GraspGen 在產生與篩選抓取姿態時，需要依據指定的夾爪幾何參數判斷候選姿態是否可執行；本研究使用 Robotiq 2F-140 夾爪設定，其描述夾爪的開口範圍、寬度、深度、接近方向與接觸區域等資訊。這些參數會影響候選 grasp pose 的尺度判斷與碰撞檢查結果，因此決定哪些抓取姿態會被保留下來作為後續執行候選。
\end{itemize}

\subsection{實驗設定}

\subsubsection{消融實驗設計}

為了評估各核心設計對整體任務成功率的影響，本研究設計 A0--A3 四組實驗條件；每組僅移除一項核心機制、其餘均與完整系統相同，以隔離該機制對閉環流程的貢獻。四組設定分述如下：

\begin{itemize}
  \item \textbf{A0（完整系統，our method）}：保留第三章所述之 VLM observe--reason 決策、多候選 ranked goal\_poses、Size Dimension 估計與 GraspGen 抓取 pipeline，作為完整方法基線。
  \item \textbf{A1（w/o VLM）}：移除 VLM 車載觀察與高層決策，改以固定流程對每個 ranked goal\_pose 依序執行一次接近與抓取；若失敗便切換至下一個 ranked goal\_pose，重複此流程直到夾取成功或所有 ranked goal\_pose 皆嘗試完畢。
  \item \textbf{A2（w/o ranked goal\_poses）}：仍保留Size Dimension 估計所產生的多個候選 goal\_pose，但移除其排序與失敗換點機制；在這些候選各自的停靠位置中，僅保留在 ROS 地圖 XY 平面上「停靠位置距目標中心最近」的一個，作為唯一停靠點。由於只剩單一候選，第一次接近或抓取失敗後即無法再透過 major navigation 切換至其他停靠點或觀察視角。
  \item \textbf{A3（w/o Size Dimension estimation）}：移除Size Dimension 估計，不呼叫 item-info A2A 服務估計物體尺寸、yaw、grasp direction 與候選品質。改為僅依目標中心與 ROS keepout map 產生候選停靠點：以目標中心為原點，朝外推一段固定距離（即 stand-off，預設 $0.6$ m），在 $8$ 個等分方向（每隔 $45^{\circ}$）各取一個候選點，並捨棄在 keepout map 上車體無法停放（footprint 範圍內含障礙）的方向。保留下來的候選點其排序僅依方向角的固定幾何順序給定（rank 即方向先後，並非如 A0 依抓取可行性與品質排序），車體朝向則一律面向目標中心。
\end{itemize}

四組條件皆保留相同任務目標、物件集合、實驗場景與成功判定方式，使結果差異主要反映被移除機制對閉環流程的影響。

\subsubsection{Measurement of System Performance}

本研究針對五種日常物件進行測試，包含 apple、doll、box、coffee 與 cup。每一組實驗條件對每個物件執行 $10$ 次 trial，因此每組條件共 $50$ 次 trial。四組消融設定 A0--A3 合計 $200$ 次 trial。實驗結果由 workflow 自動輸出的結構化結果紀錄彙整而來，每筆紀錄包含任務最終狀態、任務耗時、節點執行序列、候選 goal\_pose 使用數、導航結果、抓取結果、接近結果與失敗原因。

令第 $i$ 次 trial 的任務成功指標為 $S_i\in\{0,1\}$，其中 $S_i=1$ 表示該 trial 的最終任務狀態判定為成功。在總 trial 數為 $N$ 的條件下，任務成功率定義為
\begin{equation}
    R_{\mathrm{task}}=\frac{1}{N}\sum_{i=1}^{N}S_i.
\end{equation}

任務時間以「自Size Dimension 估計階段開始至任務結束的總時間」作為統計來源，並僅對成功 trial 計算平均值。此設計可避免失敗任務因提前終止或反覆重試而與成功任務效率混在一起。令 $T_i$ 為第 $i$ 次 trial 自Size Dimension 估計開始至任務結束所經過的時間，成功任務平均時間定義為
\begin{equation}
    \bar{T}_{\mathrm{succ}}=
    \frac{1}{\sum_i S_i}\sum_{i:S_i=1}T_i.
\end{equation}

此外，本章統計每次任務嘗試過的候選 goal\_pose 數量 $G_i$，其平均值定義為
\begin{equation}
    \bar{G}=\frac{1}{N}\sum_{i=1}^{N}G_i.
\end{equation}
此指標可反映多候選策略是否真的被使用，也能輔助解釋任務時間與成功率之間的取捨。

\subsubsection{Analysis}

本小節依 Result 呈現的順序，逐項分析造成上述結果的可能成因及其對系統設計的意義。

\paragraph{整體成功率}
A0 為四組條件中成功率最高，顯示完整系統的效益來自多個機制的共同作用。A1 移除 VLM observe--reason 後成功率下降，表示即使仍保留 ranked goal\_poses，缺少車載觀察後的高層判斷仍會降低任務穩定性。A2 移除 ranked goal\_poses 後下降最明顯，顯示單一最近停靠點不足以應對遮擋、視角不佳或抓取方向不合適等情況。A3 移除 Size Dimension 估計後，說明僅依目標中心與地圖可通行性產生候選點雖可完成部分任務，但缺少物體尺寸、朝向與抓取方向資訊時，候選點品質與後續抓取可行性皆明顯受限。進一步從任務時間與嘗試次數觀察，A2 的成功任務平均時間最短，但成功率僅 $44\%$，這代表較短時間並不表示策略較佳，而是因為 A2 只嘗試單一候選點，當該點不可行時便很快失敗，缺少透過換點恢復的能力；A0 雖然時間較長，但能在第一視角不佳時透過候選點切換與 VLM 判斷提高整體成功率。A1 平均嘗試候選 goal\_pose 數最高，成功率卻仍低於 A0，顯示同一個 goal\_pose 的接近與抓取有時會在第一次嘗試便失敗，此時應由 VLM 依當前畫面與執行紀錄判斷是否值得在同一個 goal\_pose 再嘗試一次接近與抓取，而非一次失敗便直接切換至下一個 goal\_pose 重新觀察；A1 缺少此判斷，因此即使換點更頻繁仍無法有效提升成功率。A3 平均嘗試次數雖不算少，但成功率明顯偏低，其原因並非重試次數不足，而是候選點本身缺乏物體幾何與抓取方向資訊，使停靠點可能不適合觀察或抓取。

\paragraph{各物件表現}
A0 在五個物件上皆維持高成功率，顯示完整系統對不同形狀與擺放的物件具有一定泛用性。A2 在 doll、box 與 cup 上下降特別明顯，說明單一最近 goal\_pose 對形狀、遮擋或抓取方向較敏感的物件尤其不穩定。A3 在 apple 上仍可維持高成功率，但在 cup 上明顯偏低，顯示不同物件對候選點品質與 Size Dimension 估計的依賴程度不同；其中需注意部分條件在個別物件上成功樣本過少（如 cup 於 A3 僅 $2$ 筆成功），其結果僅供參考、不宜過度解讀。

\paragraph{任務時間}
就成功任務的時間分佈而言，A0 與 A1 因可進行多候選嘗試，時間分佈較寬；A2 雖然時間較短，但對應的成功率最低，因此不宜單獨以時間作為方法優劣判準——對移動抓取任務而言，能否在第一個候選點失敗後恢復，比單次嘗試是否快速更重要。分物件來看，box 為最耗時的物件：box 為一個帶有開口的盒子，理想的夾取面應為其正面開口方向，然而本研究的 Size Dimension 估計僅能將物體近似為一個立方體 bounding box，無法區分開口面與側面；由於 box 的側面寬度較薄，依 Size Dimension 所排序的候選 goal\_pose 容易被導向較薄的側面，使原本具備 Size Dimension 與多候選能力的 A0 與 A1 反而可能選到不利夾取的角度，需反覆切換停靠點才能完成，任務時間因而最長。相對地，A3 不依賴 Size Dimension 估計，其候選點僅由目標中心、導航地圖可通行區域與物體擺放位置共同決定；在 box 此例中，這種與場景幾何耦合的選點方式恰好對應到較適合夾取的方向，使 A3 在 box 上同時取得較短的任務時間與不低的成功率。A2 在多數物件上時間最短且分佈最窄，但這是因為其僅嘗試單一 goal\_pose、成功樣本偏少，「時間較短」其實是快速成功或快速放棄的結果，而非效率較佳。

\paragraph{節點耗時}
就各節點的耗時組成而言，A0 額外包含 observe--reason 流程，其 reason node 需要額外推論成本，但此成本換來較高的整體成功率。A1 移除此部分後並未達到更高成功率，表示省略高層觀察決策雖可減少部分推論時間，卻會在後續失敗重試中付出代價。A2 的成功任務時間較短，主要來自不進行多候選恢復；然而這種時間下降伴隨顯著成功率下降，因此並非有效的整體任務改善。

\paragraph{候選 goal\_pose 嘗試數}
A2 因設定上只保留最近的單一 goal\_pose，所有 trial 的嘗試候選數皆為 $1$，因此無法在視角或抓取條件不佳時透過切換停靠點恢復。A0 在多數任務中仍可於第一個候選點完成，但在必要時會嘗試後續候選點，使系統兼具效率與恢復能力。A1 的平均嘗試候選 goal\_pose 數高於 A0，反映固定流程在失敗後仍會繼續換點，但因缺少 VLM 對觀察品質與抓取時機的判斷，更多換點並未帶來更高成功率。分物件來看，box 明顯需要最多次候選嘗試，且與其任務時間最長的觀察一致；如前所述，這是因為 Size Dimension 估計將 box 近似為立方體 bounding box、無法區分開口面與較薄的側面，使 A0 與 A1 排序出的候選 goal\_pose 容易先被導向不利夾取的方向。A3 在 box、cup 與 coffee 上的平均嘗試數偏低，因其僅依固定方向產生候選點，常在少數嘗試內即成功或耗盡。

\paragraph{失敗模式}
最常見的失敗為候選 goal\_pose 全數用盡，表示任務失敗多半不是單一節點立即崩潰，而是在可嘗試的停靠點皆無法導向成功抓取後結束；此類失敗在 A2 特別明顯，直接反映單一最近候選點的限制，A1 亦因缺少 VLM 判斷而可能在不合適視角中反覆嘗試。候選 goal\_pose 全數用盡之所以成為最主要的失敗型態，並非單一原因造成的即時錯誤，而是接近與抓取階段多項失敗累積後的最終結果。在 car\_approach\_node 實際執行底盤接近與手臂抓取時，有許多因素可能造成該次抓取失敗：其一，AMCL 定位（AMCL pose）存在誤差，使系統對車體與目標相對位置的估計失準；其二，GraspGen 產生的 6-DoF 抓取姿態本身未必精確，與目標實際可夾取位置存在偏差；其三，手臂 IK 求解所設定的末端位置與角度容許誤差範圍若過大，雖能求得解，卻可能在實際執行時對不準目標而夾取失敗；其四，車體在接近過程中未停到預期位置，導致距離目標過遠、超出手臂可達範圍而無法完成夾取；其五，部分候選 goal\_pose 對應的停靠點本身即不利於接近與抓取，例如周圍可用空間狹窄或可行接近方向受限。由於上述任一情況都會被判定為該候選點抓取失敗，workflow 隨即切換至下一個候選 goal\_pose 重新嘗試；當這些因素在多個候選點上反覆發生時，系統便會在所有 ranked goal\_pose 皆嘗試過、卻仍未成功抓取的情況下結束，最終被記錄為候選 goal\_pose 全數用盡。換言之，此類失敗反映的往往不是換點機制本身失效，而是接近與抓取執行階段的精度與可行性限制。

A3 的失敗型態與 A2 不同，其導航途中碰撞（$7$ 次）與路徑過窄、抓取後無法返家（$3$ 次）的次數遠高於其他條件；這表示只用目標中心與 keepout map 產生候選點時，雖可排除部分不可通行位置，但仍不足以保證候選點在導航、抓取與返航三者之間同時合適，而完整系統的 Size Dimension 估計不只是提供物體位置，也間接影響停靠點與抓取方向的選擇，因此能降低此類導航與執行階段的失敗。最後，A0 仍有少數失敗，其中多數為候選 goal\_pose 全數用盡，另有一次為 YOLO 偵測或追蹤不到目標，顯示完整系統雖能提升成功率，但仍受上游偵測穩定性與候選點覆蓋範圍限制；若要進一步提高成功率，應優先改善兩個方向：其一是提高目標偵測與 instance tracking 的穩定性，其二是讓候選 goal\_pose 生成能覆蓋更多可觀察與可抓取的方向，同時避免增加過多低品質候選造成任務時間膨脹。

\subsubsection{實驗小結}

本章以 $200$ 次 Unity 數位孿生實驗驗證本研究系統設計。結果顯示，完整系統 A0 達到 $90\%$ 任務成功率，優於移除 VLM observe--reason 的 A1（$78\%$）、移除 ranked goal\_poses 的 A2（$44\%$）與移除 Size Dimension estimation 的 A3（$68\%$）。消融結果說明，本研究的成功率並非由單一模組造成，而是來自三個機制的共同作用：Size Dimension 估計提供較合理的候選停靠點基礎，多候選排序使系統具備失敗後換點能力，VLM observe--reason 則根據車載觀察決定是否進入抓取或切換視角。

\section{Conclusions and Future Works}

\subsection{Conclusions}

本論文根據目前專案實作，整理並形式化一套以 VLM 與代理人架構為核心的居家輔助機器人系統。系統透過 LangGraph 維護長任務狀態，以 A2A 協議呼叫 GPU 推論服務，並結合 ROS2/Nav2 與 Unity 數位孿生環境完成移動抓取流程。VLM 不直接輸出低階控制，而是在結構化動作集合中選擇下一個代理人模組，使高層語意判斷與低層幾何控制分離。

方法上，本研究將可確認的系統流程表示為狀態、觀察、動作與評估目標，並補充 Unity-to-ROS map 座標轉換、導航目標朝向、地圖可行的 goal\_pose ranking、抓取姿態排序、底盤靠近取樣與任務成功條件。相較於單次感知或單次 VLM 推理流程，本系統的關鍵特徵在於狀態持續性、模組邊界清楚、失敗後可重新估計與候選導航點可切換。

第四章進一步以 A0--A3 共 $200$ 次 Unity 數位孿生消融實驗驗證系統設計。結果顯示，完整系統 A0 在其 $50$ 次 trial 中達到最高任務成功率，且移除 VLM observe--reason、ranked goal\_poses 或 Size Dimension estimation 皆會造成不同程度的成功率下降。這說明本研究的效益並非來自單一模組，而是由Size Dimension 估計、多候選導航點排序與車載觀察決策共同形成可恢復的閉環流程。

\subsection{Limitations}

目前系統限制可分為四類。第一，多視角 Size Dimension 依賴世界座標資料、camera calibration 與 bounding box 品質；若上游資料錯誤，候選導航點與 grasp generation 會受到影響。第二，VLM 的決策品質受 prompt、車載影像與歷史摘要限制，當觀察不足時仍可能需要多次導航。第三，grasp pose 需經過 camera、PyBullet、ROS map 與 robot base 等座標轉換，任何座標不一致都可能造成靠近或抓取失敗。第四，部署涉及 Unity、ROS2、A2A server、模型權重、Nav2 map、keepout map、相機 topic 與控制節點，維護成本高於單一模組系統。

\subsection{Future Works}

後續工作建議如下：
\begin{enumerate}
  \item 擴充 trace-based 實驗至更多物件、更多初始位置與不同遮擋程度，以驗證目前 A0--A3 結論在更大場景變化下是否仍成立。
  \item 將 Size Dimension 估計的不確定性量化，讓 goal\_pose ranking 不只依 feasible count 與 confidence，也能納入位置與Size Dimension 估計可信度。
  \item 增加自動化場景重置與批次實驗腳本，使不同目標物、遮擋程度與初始位置可重複執行。
  \item 補足 place 任務或明確界定本文只處理 pick-and-return，避免論文宣稱超出目前 workflow 能力。
  \item 將 VLM provider、模型版本、權重來源與資料傳輸方式寫入實驗設定，以支撐隱私與本地部署宣稱。
  \item 擴充 trace visualization，將 VLM 決策、導航 rank、抓取候選與 car-approach phase 轉為可檢查圖表。
  \item 擴充更多居家任務設定，並於未來進一步進行實體環境驗證，以確認系統在真實感測雜訊與硬體誤差下的穩定性。
\end{enumerate}

\subsection{Chapter Summary}

本章總結目前系統的可確認貢獻與限制。整體而言，本研究已具備從自然語言輸入到移動抓取控制的完整代理人式流程，並透過第四章 A0--A3 消融實驗顯示各核心機制對成功率的貢獻。下一階段工作的重點，是將目前在數位孿生環境中驗證的流程擴展至更多場景條件與實體平台，以進一步確認系統在真實感測雜訊與硬體誤差下的穩定性。
